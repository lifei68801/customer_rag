# 租户边界按隔离要求划，不按人设划；数字人从租户上摘下来

**Status**: proposed

spec `2026-09-08-interaction-redesign-design.md` 的 D1 定了「数字人 = 租户」：
一个数字人就是一个租户，一整套本体 + 一整张图 + 会话 + 记忆。这条判断在它自己
举的例子里是对的——muji-商品 / muji-门店 / muji-供应链，三个数字人的数据源、
本体、图谱本来就是三套，这时「数字人 = 租户」不是耦合，是同一件事的两个名字。

但把这条判断当成建租户的**方法**用，会画错边界。因为它让"要几张脸"直接决定
"切几刀隔离"，而这两件事在业务上是独立的。

## 现状里两个不对称的事实

**「数字人」这个概念几乎没有重量。** `tenant_personas` 只有三个展示字段：
头像、一句话、引导问题。它对问答行为**零影响**——`app/agent/graph.py` 的
`_PROMPT_TEMPLATE` 是模块级常量，没有按租户配的系统提示词、语气、工具权限。

**「租户」这个概念极重。** 15 张业务表按 `tenant_id` 隔离，
`app/graphrag/neo4j_client.py` 里 199 处 `tenant_id`，实体身份是
`(tenant_id, node_key)`（SQLite 主键与 Neo4j `MERGE` 键都是），检索、会话、
记忆、诊断、数据源全部按租户切。

而且跨租户不只是"不支持"，是**被主动判为缺陷**：`neo4j_client.py` 的脏边检测
里有一类叫 `cross_tenant`，两端节点分属不同租户的边会被报成脏数据清理掉。

所以「数字人 = 租户」这个等式里，等号右边扛着全部重量，左边几乎是空的。
切一张脸的代价是切掉整个知识库。

## 边界画错时会撞上什么

典型业务里，"需要一起查"和"需要互相看不见"这两条线**不重合**：

- 商品 × 门店：要跨着查（「这款商品哪些门店有货」），权限上不必互相隐藏
- 商品 × 供应链：权限要隔离（店员不该看到采购成本），也不需要跨着查

按人设划的话，三个数字人 = 三个租户 = 三刀。于是商品 × 门店这一对被切开了
——而它本不该被切开。结果是「这款商品哪些门店有货」这种最自然的问法，
在结构上答不出来，而且用户看不出原因：问答未命中页会记一条 `no_match`，
但页面上写的是「本体里没有这个概念，去建模」，实际原因是"这个知识在另一个
数字人那里"。用户照着提示去建模，建出来的是一份重复的门店数据。

## Considered Options

- **保持现状，跨查答不了**：用户人工拼两次查询。代价落在人身上而不是系统里，
  而且不可见——没人知道有多少问题是这么丢的。
- **合并租户 + 在租户内加"人设可见范围"**：这是给隔离加第二条维度，正是
  D1 因为"今年已经出过四次跨领域泄漏"而明确否掉的做法。漏掉任何一处过滤
  就是泄漏，而这类漏在测试里不红、在生产上返回 200。
- **允许跨租户的边**：要改脏边检测的判据，且一次问答会混进两套本体的概念。
- **（选定）租户 = 隔离单元，数字人 = 展示单元，一个租户可挂多张脸**：
  能一起查且权限相同的领域合并成一个租户，权限必须隔离的保持独立租户；
  数字人从租户上摘下来，`tenant_personas` 主键从 `tenant_id` 改成
  `(tenant_id, persona_id)`。隔离仍然只有一条维度（`tenant_id`，二元、
  久经考验），D1 的教训不被推翻；而"几张脸"不再强迫"切几刀"。

## 建租户时该问的三个问题

按顺序问，答案决定刀画在哪：

1. **这两块知识需要一起被查到吗？** 需要 → 倾向同一个租户。跨租户在这个
   架构里是结构性不可能，不是"以后再说"。
2. **有没有人只能看其中一块？** 有 → 必须是两个租户。这一条压倒第 1 条：
   宁可某些问题答不出来，也不能泄漏。
3. **前两问的答案冲突吗？**（同一对既要跨查又要隔离）→ 那是真矛盾，必须
   选一边，并把选择记下来。多数情况下不冲突——冲突时先检查"要隔离的到底
   是整个领域，还是只是成本、报价这几个字段"。

"要几个数字人"**不在这三问里**。脸的数量是展示决策，跟隔离无关。

## Consequences

- `tenant_personas` 主键改为 `(tenant_id, persona_id)`；`chat_sessions` 要
  带上 `persona_id`（spec 裁决补充「一个会话属于一个数字人」今天是免费的，
  因为 persona == tenant，解耦之后要显式维护）。
- 前台右栏从"切租户"变成"切脸"：`ChatPage.tsx` 现在是
  `onSelect={setTenantId}`，切脸会换掉整个知识库。解耦后切脸不换租户。
- 看板的"一个领域一张卡"仍按租户，不按脸——卡上的数字是隔离单元的数字。
- **这条 ADR 不改变任何已有租户。** 写它的时候库里只有一个租户
  （`demo`，20017 个实体）有真实数据，`tenant_personas` / `user_tenants` /
  `organizations` 全是空表，多数字人一次都没被真实用起来。也就是说：
  **现在是修这个边界成本最低的时刻，没有存量要迁**。等三个数字人各自建完
  本体、导完数据之后再改，就要改写每行和每个 Neo4j 节点的 `tenant_id`、
  合并两套本体、处理同名不同义的实体。
- 合并两个租户时有一个反直觉的好处：同 `term_type` 同名的实体会自动变成
  同一个节点（`node_key` 是 `类型:标准名`），门店那边的库存边会直接连到
  商品那边的 `产品:Beer`——这正是要的跨查能力。真正的冲突面只有"两边都
  定义了同名实体类型但字段不同"。

## 这条 ADR 不主张的事

- 不主张给数字人加行为（系统提示词、语气、工具权限）。今天 persona 对问答
  零影响是个干净的现状；一旦它能改变答案，它就成了第二条影响**正确性**的
  维度，而正确性问题比外观问题难查一个数量级。要加的话单独立一条 ADR。
- 不主张现在就合并 `demo` 或任何存量租户。
