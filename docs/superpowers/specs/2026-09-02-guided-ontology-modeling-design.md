# 引导式本体建模设计

> 日期：2026-09-02
> 状态：设计定稿，待转实现计划
> 范围：管理后台「建模」组。引导负责从零到一，现有三个 tab 保留做后续微调。

## 1. 问题

新用户建不出本体。当前流程要求他在**碰到自己的数据之前**，先凭空产出三样东西：

1. 实体类型（还要为每个类型想好有哪些额外字段、字段是什么类型）
2. 关系类型（大写、下划线、还要填一个 example_phrase 和一个叫 `allow_chain_query` 的开关）
3. 约束（`(主语类型, 关系类型, 宾语类型)` 三元组）

而且这是**硬门槛**：`admin_schema_etl_routes.py:129` —— 本体没确认，表格导入页根本进不去。

这套流程假设用户已经知道自己领域里有哪些实体类型。**新用户不知道，那正是他来找引导的原因。**

### 1.1 现有资产

三件已经存在、但用错了位置或没被利用的东西：

| 已有 | 现在用在哪 | 本设计怎么用 |
| --- | --- | --- |
| 读表头列名（`tableHeader.ts`） | ETL 配置页，流程末端 | 提到最前面，作为引导的起点 |
| ETL 映射配置构建器（`schemaEtlConfigBuilder/`） | 用户建完本体后手工配 | 引导过程中顺带产出，不用重配 |
| draft / confirmed 生命周期 | 三个 tab | 不变，引导产出的是 draft |

### 1.2 参照：Foundry 的做法

Palantir Foundry 的 object type 是**从 dataset 长出来的**，不是凭空设计的：先有数据集，把列映射成属性，把外键映射成 link type。本设计沿用这个方向——**数据优先，不是本体优先**。

（Foundry 把 Ontology Manager 和 Object Explorer 做成两个独立应用，分界是「定义 vs 实例」。本项目已经按这个分法组织了侧边栏，见 `adminRoutes.ts` 的注释。）

### 1.3 一个真实样本

`demo` 租户的本体，形状就是从一张电商订单宽表推出来的：

```
订单号 ─[CONTAINS]→ 产品 ─[BELONG_TO]→ 类目
  │  └─[ORDER_BY]→ 用户名        └─[SOLD_BY]→ 公司
  └─[SOLD_BY]→ 公司

订单号.属性: revenue, units_sold, profit, cost_of_goods_sold, purchase_date
用户名.属性: customer_state, customer_city, customer_zip
```

标准星型模式：订单号是事实，其余是维度。本文档所有例子都用这份数据，因为它是真的。

注意 `customer_state` 被做成了属性而 `产品` 被做成了实体——**光看数据这两者分不开**，它们都是低基数字符串列。这个岔路口是本设计的核心。

## 2. 设计决策

| # | 决定 |
| --- | --- |
| 1 | 引导从**用户的一张真实业务表**开始，不是问卷、不是模板 |
| 2 | 平台推荐**一整套草案**让用户审阅，不逐列问答 |
| 3 | 统计量在**前端全量扫描**得出，数据不出用户的机器 |
| 4 | 数据形状能定的直接定；低基数列用**「你会问哪类问题」**来定，**默认倾向实体** |
| 5 | 关系用**默认星型 + 图上改挂 + 命名**；**「约束」这个概念对用户消失** |
| 6 | 产出草稿 + 一张图 + **未使用列清单**；确认本体与跑数据分两步，但映射不重配 |
| 7 | 引导是**首次建模**的入口；三个 tab 保留做后续微调，两条路径长期并存 |

### 逐条理由

**决定 1（数据优先）**：用户的业务知识是以「我有一张订单表，有这些列」的形式存在的，不是以「我的领域有哪些实体类型」的形式。而且最难的那个判断只有对着真实数据才做得了——凭空问「州该不该建成实体」没人答得上来。

**决定 2（整套草案）**：本体是一个**结构**，不是一串独立决定。逐列问答答完 13 次，用户仍然不知道自己建出了什么形状；一次看到「订单号连着 4 个东西」这张图，他才能说出「不对，公司应该通过产品连」——那是业务知识真正起作用的地方。

**决定 3（前端扫描）**：建模阶段数据不出机器，对数据敏感的场景是实打实的加分项，且不改现有的上传时机。代价是算不了列间函数依赖（`city → state` 这类信号），接受。

**决定 4（默认倾向实体）**：两个方向的错误代价不对称——

- **多建了实体**：图谱里多几个节点，查询照常，只是有些节点没用。**看得见**（实体列表里就有），改起来是删除。
- **少建了实体**：那类问题就是答不出来，不报错、不告警。用户只会觉得「这系统不太行」。要修得重跑 ETL。

少建是静默错误，多建不是。所以默认往实体偏。

**决定 5（约束消失）**：`term_type_relation_allowlist` 本质上就是「哪些关系存在」的记录。用户画出的图**就是**这张表，不需要再让他理解一个叫「约束」的概念并单独配一遍。用户要理解的概念从三个（实体类型 / 关系类型 / 约束）降到两个，而且都是图上看得见的东西。

**决定 6（未使用列清单）**：一张 30 列的表，引导可能只用了 13 列。剩下 17 列如果不显示，用户永远不会知道自己丢了什么——他会在三个月后问「为什么查不到发货地址」，而那一列从一开始就没被采纳。**不显示等于静默丢弃。**

**决定 7（两条路径并存）**：引导解决从零到一，三个 tab 解决「已经有本体了，我要加一个字段」。后者用引导做反而绕。代价是两套 UI 要维护——接受，因为它们的用户和场景确实不同。

## 3. 列角色判定

### 3.1 需要的统计量

前端扫描整个文件，对每列收集：

| 统计量 | 用途 |
| --- | --- |
| 非空值总数 | 分母 |
| 不同值个数（**带上限**） | 判定基数高低 |
| 推断类型（数值 / 日期 / 字符串） | 判定度量、日期 |
| 前若干个样例值 | 展示给用户，让判断有依据 |

**distinct 集合必须设上限**（建议 1000）：一旦某列超过上限就停止收集、标记为「高基数」。判定只需要知道低基数还是高基数，不需要精确数字；有了上限，10 万行的表在浏览器里内存也可控。

**不采样。** 前 N 行不是随机样本——订单表通常按时间排序，前 1000 行可能只有 3 个州，基数估计会严重偏低，把本该是实体的列判成属性。这类错误不会报错，只会让本体建歪。

### 3.2 自动判定（不问用户）

| 数据形状 | 判定 | demo 中的例子 |
| --- | --- | --- |
| 数值类型 | **属性**（度量） | `revenue` `profit` `units_sold` `cost_of_goods_sold` |
| 字符串，不同值数 ≈ 非空行数 | **本行的标识** | `订单号` |
| 字符串，高基数但重复明显 | **属性**（自由文本） | 备注、描述类 |
| 可解析为日期 | **属性**，并附带警告（见 3.4） | `purchase_date` |

### 3.3 需要用户判断：低基数字符串列

这是唯一的模糊地带。`产品` `公司` `类目` `用户名` `customer_state` `customer_city` `customer_zip` 全在这一类。

平台**不问**「它该是实体还是属性」（用户答不了），而是把两条路的**能力差别**摆出来：

> **`customer_state`** — 50 个不同值，样例：`CA` `TX` `NY`
>
> - 建成**实体类型** → 能问：「加州有哪些客户」「哪个州订单最多」「跟这个客户同州的还有谁」
> - 做成**属性** → 只能：查订单时按州过滤，问不出上面那些
>
> 你的业务里会问上面那类问题吗？ ( ) 会，建成实体 　( ) 不会，做成属性

默认选中「建成实体」（决定 4）。

### 3.4 日期列的已知限制

数据模型只支持 `string / number / integer / number[]`（`ontology_categories.py` 的 `_VALID_EXTRA_FIELD_VALUE_TYPES`），**没有日期类型**。日期列会被存成 `string`，这意味着「上个月的订单」这类问题在图谱层做不了范围过滤。

平台识别出日期列时**必须明说这个限制**，而不是默默存成字符串。这不在本次改造的修复范围内（要动数据模型和查询层），但用户有权在建模时就知道。

## 4. 关系推导

### 4.1 默认星型

同一行里出现的两个实体列，之间就存在关系。但一张宽表里 5 个实体列两两组合有 10 对，而 demo 只需要 5 条——多出来的是**冗余**（`订单号 → 类目` 该走 `订单号 → 产品 → 类目`）。

**这个层级判断是纯业务知识，平台推不出来。** 所以：

1. 平台给出**最安全的默认**：标识列（订单号）连向所有维度，画成一张星型图
2. 用户在图上**改挂**：把「类目」从订单下面拖到「产品」下面
3. 用户给每条边**命名**

星型作为默认的理由：它一定是**连通**的，不会漏掉任何实体；而多一条冗余边是**看得见**的——图上摆着，用户一眼就说「这条不对」。反过来若默认不连、让用户自己加边，漏掉的那条不会有任何提示。

### 4.2 关系命名

- 名字必须匹配 `^[A-Z][A-Z0-9_]{0,63}$`（`ontology_relations.py:24`）。平台按列名给建议，用户可改。
- **已有的关系名要列出来供选**：demo 里 `SOLD_BY` 用了两次（`订单→公司` 和 `产品→公司`）。不给选的话会建出 `SOLD_BY` 和 `SELL_BY` 两个同义关系。
- `example_phrase` 由平台自动生成（取样例值填模板），不问用户。
- **`allow_chain_query` 不暴露给用户**，默认开（demo 的 4 个关系全是 1）。它是查询层的开关，普通用户没有判断依据；需要时在关系类型 tab 里改。

### 4.3 约束由图生成

`term_type_relation_allowlist` 的每一行 = 图上的每一条边。用户不需要知道这张表存在。

## 5. 产出与衔接

### 5.1 审阅视图

引导走完，用户看到三块：

1. **那张图** — 实体 + 关系，可改挂、可改名
2. **每个实体的属性列表** — 哪些列成了它的属性
3. **未被使用的列** — 见决定 6，这块不可省

### 5.2 一并产出 ETL 映射

引导过程中收集的信息，已经足够生成 `schemaEtlConfigBuilder` 需要的全部内容：

| `BuilderEntity` 字段 | 引导中的来源 |
| --- | --- |
| `termType` | 用户确认的实体类型 |
| `standardNameColumn` | 那个低基数列本身 |
| `nodeKeyParts` | 同上（单列 `{kind:'column'}`） |
| `fieldMappings` | 判定为属性的那些列 |
| `fileId` | 用户传的那张表 |

`BuilderRelation` 的 `subjectTermType / relationType / objectTermType` 直接来自图上的边。

产出交给现有的 `buildConfigYaml()`，不新写一套 YAML 生成。

### 5.3 两步，不合并

```
传表 → 审阅这张图（改挂、命名）→ ① 确认本体 → ② 跑第一批数据
```

① 和 ② **是两个动作，不合并**：确认本体是不可逆的（旧的已确认版本会被换掉，见 `describeConfirmDiff`），而跑数据可以先不跑。但 ② 不该让用户重新配一遍映射。

对比现状：

```
现在：建实体类型 → 建关系类型 → 配约束 → 确认 → 进 ETL 页
      → 传表读列 → 配实体映射 → 配关系映射 → 生成 YAML → 跑   （10 步）

引导：传表 → 审阅 → 确认 → 跑                                （4 步）
```

中间 5 步不是被省略，是**它们的信息在前两步就已经收集完了**，再问一遍是重复劳动。

### 5.4 与三个 tab 的关系

- 引导产出的是 **draft**，走现有生命周期，不新建一套状态
- 引导结束后，用户随时可以去三个 tab 手工微调
- 三个 tab 的行为完全不变
- 本体已确认的租户，引导入口应当明确提示「这会覆盖当前草稿」

## 6. 范围外

- **多表引导。** 首版只支持一张表。多表要处理跨表外键，是另一个量级的问题。
- **列间函数依赖分析**（`city → state`）。它需要后端算，与决定 3 冲突。
- **日期类型支持。** 只做提示，不改数据模型（见 3.4）。
- **从已有数据反向重建本体。** 引导只处理「新表 → 新本体」。
- **行业模板。** 没有表可传时的退路，本版不做。

## 7. 未决风险

1. **前端扫描大文件的实际表现未实测。** 10 万行 CSV 在浏览器里流式扫描应当在几秒内，但 xlsx 要先 `arrayBuffer()` 全读进内存（现有 `tableHeader.ts` 已经这么做了，只是加了 `sheetRows: 1`）。百万行级 xlsx 可能卡死页面。实现时需要实测并定一个明确的行数/体积上限，超过就拒绝并说明原因——**不能让页面静静地卡住**。

2. **「你会问哪类问题」这个提问方式未经真实用户验证。** 它比「实体还是属性」好答，但仍然假设用户能预见自己未来的问题。真实效果要等有人用过才知道。

3. **星型默认对非星型数据会很别扭。** 如果用户的表不是事实表（比如一张纯粹的产品主数据表，没有明显的标识列），星型默认可能给出奇怪的结构。这类表的表现需要在实现时用真实样本试过。

4. **两条路径并存的长期成本。** 引导和三个 tab 会分别演化，某天可能出现「引导建得出、tab 改不了」的组合。
