# 管理后台操作顺序的连续性 —— 设计

**目标：** 让「本体构建 → 数据上传加工 → 映射」这条主路径在界面上是连续的：系统已经知道的事不再让用户重新供一遍，产品已经知道的下一步不再让用户自己去侧边栏找。

**范围：** 管理后台的流程接缝。不改本体模型、不改 ETL 语义、不改任何后端算法。

**产生方式：** 2026-09-03 对当前后台操作顺序的逐分支盘问，七条裁决。本文是那次对话的结论。

---

## 背景

后台的导航结构本身是设计过的，而且理由写在 `frontend/src/adminRoutes.ts` 的注释里：路径按工作阶段分段（`model` → `ingest` → `review`），侧边栏分组与之一一对应，顺序即依赖顺序——ETL 会拒绝未确认本体的租户（`app/api/admin_schema_etl_routes.py::_build_sample_files`），文档管线在本体未确认时会跳过图谱抽取（`app/ingestion/pipeline.py`）。

盘问发现的问题不在这个结构上，而在**结构与结构之间的接缝**。七处问题归成三个形状。

### 形状一：系统已有的东西，让用户再供一遍

出现三次。

1. **引导产出的 ETL 映射走文件系统绕一圈。** `GuidedOntologyPage` 的完成页给一个「下载 ETL 映射配置」按钮，把系统自己算出来的 YAML 交给用户保管，用户再到表格导入页手工传回来。中途可能关标签页、在下载目录里找不着、或者过两天分不清哪个 YAML 对应哪个租户。
2. **表格导入页第一屏邀请他从头配一遍。** `SchemaEtlPage` 的 `builderExpanded` 默认 `true`，开门见山就是「配置构建向导：对着自己的数据列一步步配出 config.yaml」。刚走完引导的用户看到的是一个邀请他重做已完成工作的界面，而界面没说他的映射在哪。
3. **预演之后要正式执行，得把文件再传一遍。** `POST /runs` 是唯一的写入入口，每次都要 `config` + `data_files` 全新上传，没有「把这次预演转成正式执行」的路径。而空状态自己写着「首次运行建议勾选『预演』」——产品在推荐一条它自己没铺好的路：照做的人多传一遍文件，不照做的人一步到位。**推荐的路比不推荐的路更贵**，结果是没人预演。

### 形状二：产品知道，但不说

1. **做完一步不告诉你下一步。** 后台已经有两条出口：「这里是空的，你该先去哪」（`emptyStateLinks.test.tsx` 是一条仓库级约定，还测链接文字必须精确匹配侧边栏标签）和「有活等着你」（`useNavBadges` + `NavBadge`）。缺第三条：本体结构页确认成功只弹一个 toast「已确认」，该页两条 `ADMIN_ROUTES` 链接一条往回指（引导页），一条横向指（本体图，同属建模阶段），没有一条指向下一阶段；`SchemaEtlPage.tsx` 里 `ADMIN_ROUTES` 引用数为零，连它自己那句「请先完成本体 schema 确认后再触发 ETL」都不是链接。徽标补不上这个洞——待审关系能计数，「你该去传数据了」不能。
2. **重新建模会让已有数据失效，确认框不说。** `confirm_ontology` 只动三张本体表，完全不碰 `terms`，确认前也不查已有实体。一个已经装了 9335 个「客户」实体的租户，重跑引导（`replace_draft` 是整份替换）再确认，若新本体里没有「客户」这个类型，那 9335 条实体原地留在 `terms` 表里但不再属于任何已确认类型，对下游查询不可见。确认框会说「删除实体类型 客户」，不会说「这会让 9335 条已有实体失效」。

### 形状三：说的和做的不一致

1. **落地路由跳过第一阶段。** `App.tsx` 的 `/admin` 索引路由 `Navigate to={ADMIN_ROUTES.documents}`，落在「接入数据 › 文档上传」——正是导航注释里写着「把接入排在前面等于教用户走一条产品会拒绝的路」的那一段。这不是静默失败（`DocumentsPage` 会检测本体未确认、禁掉「建图谱」勾选并明说「抽取不出图谱」），但新租户第一屏是一个主能力被禁用的页面，而修复动作要他自己去另一个分组里找。
2. **两个向导的名字读起来是同一件事。** 「配置构建向导」和「从表格开始引导建模」，用户光看名字分不出该用哪个。

### 一个被盘问推翻的猜测

两个向导**不是重复，是互补**，而且共用同一套底层（引导页直接 import `schemaEtlConfigBuilder/buildConfigYaml`、`tableHeader`、`types`）：

| | 输入 | 输出 | 用在什么时候 |
|---|---|---|---|
| 引导式本体建模 | 一张表 | 本体 **+** 映射 | 本体还不存在 |
| 配置构建向导 | 已确认的本体 + 一张表 | 只有映射 | 本体已存在，再接一张表 |

方向相反：一个从表推本体，一个把表映射到已有本体。分工是对的，只是名字没把它说出来。本设计不合并它们。

## 设计

### 1. 落地路由按本体确认状态分流

`/admin` 索引路由改为：读该租户的本体确认状态，未确认 → `ADMIN_ROUTES.ontology`，已确认 → `ADMIN_ROUTES.documents`。

**为什么不静态选一个。** 侧边栏顺序表达的是依赖，落地路由跳过第一段等于产品在做和自己说的相反的事。但静态落在「本体结构」对老租户同样是错的——他们天天来传文档，不该每次被丢回建模页。这条依赖本来就是状态相关的，静态选任何一个都必然对一半人是错的。

**代价**：多一次 `/api/admin/ontology/{tenant}/status` 请求，首屏有一次重定向。状态未知（请求未回）时不要抢先跳转，也不要停在空白页——见「未知态」一节。

### 2. ETL 映射存进本体草稿

新增一张与本体同生命周期的表，持有引导流程产出的 ETL 映射：

```
ontology_etl_mapping(
  tenant_id TEXT NOT NULL,
  status    TEXT NOT NULL,          -- 'draft' | 'confirmed'
  config_yaml TEXT NOT NULL,
  source_file_name TEXT NOT NULL,   -- 产出这份映射的那张表的文件名，用于界面说清来源
  created_at TEXT NOT NULL,
  PRIMARY KEY (tenant_id, status)
)
```

把表名加进 `app/graphrag/ontology_lifecycle.py` 的 `_TABLES_WITH_TENANT_LIFECYCLE`，即可白拿 `confirm_ontology` 的原子提升——那个循环对每张表做「删 confirmed + 把 draft 提升成 confirmed」，对任何带 `tenant_id`/`status` 两列的表都成立。

三条约束：

- **`has_draft_in_any_table` 的判定不加这张表。** 只有映射、没有本体草稿时不该触发确认；确认早退时映射留在 draft，这是对的。
- **`checkout_draft` 要对称地把这张表一起复制。** 否则检出后映射消失，用户在本体结构页改两笔再确认，映射就没了。
- **`replace_draft` 写本体草稿时一并写映射。** 引导流程一次提交同时产出两者。

**为什么是「存进草稿」而不是「存在别处」。** 判据是归属，不是省一步。这份映射描述的是「这个本体的实体从哪张表的哪几列来」，它本来就是本体定义的一部分。Palantir Foundry 也是把背书数据集（backing dataset）挂在对象类型定义上，而不是让用户另外保管。同生命周期还顺带解决一个现在没人管的问题：用户重跑引导覆盖了草稿，旧映射还躺在他的下载目录里，两者已经对不上，而没有任何东西告诉他。

**明确否决的两个替代方案。** 存 `sessionStorage`：换设备、换浏览器、关标签页都会静默丢失，按本项目的判据，静默丢失比多点两下更糟。把「确认」并进引导让它一条龙：确认不可逆，且会架空本体结构页那三个 tab 的复核——引导的复核用「哪列是实体」的话术，本体页用「实体类型/关系类型/约束」，两套词汇看的是不同的东西，不能互相替代。

**「下载 ETL 映射配置」按钮保留**。它现在是备份/带走的手段，不再是交接的唯一通道。

### 3. 表格导入页首屏按映射来源分流

`SchemaEtlPage` 第一屏改为两种形态：

- **已确认本体带有映射**（来自引导）：主区域说明「引导流程已为这个本体配好映射（来自 `orders.csv`），传入数据文件即可运行」，只要求数据文件。配置构建向导降级成折叠的次级入口，标题为「改这份映射／再接一张表」。
- **没有映射**：维持现状，配置构建向导为主。

**为什么不把映射预填进构建器。** 那样界面显示的东西和实际生效的东西会脱钩——用户在构建器里改了几笔，以为改的是那份绑定草稿的映射，实际是本地状态，跑的时候以哪个为准？这正是引导流程里刚修过两遍的形状（界面显示一条不会被提交的边）。分流把「这份映射从哪来」摆在明面上，改它是一个显式动作。

### 4. 确认框对破坏性变更附带数据影响

`OntologySchemaPage` 的确认差异（`describeConfirmDiff`，`OntologySchemaPage.tsx:35`）在「删除实体类型 X」「重命名实体类型 X→Y」这类条目上，附带该类型当前的实体条数：

> 删除实体类型「客户」——当前有 9335 条实体，确认后将不再属于任何已确认类型

**为什么不加硬闸门。** 「有实体在用的类型不许删」最安全，但本项目没有批量迁移实体类型的入口，硬闸门等于给用户一扇锁死的门。本设计只让他知道自己在换掉什么，不阻止他。

**为什么值得做。** 确认框现在说「旧的已确认版本会被换掉、无法恢复」，用户理解成「本体定义会被换掉」——没错，但不完整。真正的后果在数据侧，而那一半没说。这条让「不可逆」三个字有内容。

条数按 `terms` 表中该 `tenant_id` + `term_type` 的行数统计。差异计算已经要读已确认版本，多一次聚合查询。

### 5. 前向链接与租户开局进度

**5A（本次做）** 三个完成点加前向链接，复用 `emptyStateLinks` 约定（链接纯文本 = 侧边栏标签，已有测试守着）：

| 完成点 | 链接到 |
|---|---|
| 本体结构页确认成功 | 表格导入 |
| 表格导入首次成功运行 | 实体列表；若有待审关系则同时给「待审关系」 |
| 引导流程完成页 | 已有「本体结构」，不改 |

**5B′（后续做）** 租户列表显示每个租户的开局进度（本体草稿／已确认／已导数据／有待审），点进去直达卡住的那一步。

**为什么 5B′ 不是「新手清单」。** `app/api/admin_tenant_routes.py` 整个路由挂着 `require_admin_role`——租户只能由 admin 开通，没有自助注册路径。走这条从零路线的永远是运营方自己，而且反复走。给这种人一个常驻的教学清单是永久噪音，他第二个租户开始就不看了。同一份状态对他有一个完全不同、更值钱的用法：不是「教我下一步做什么」，是「我这些租户里哪几个卡在半配置状态」。5A 是「在租户内往前推一步」，5B′ 是「在租户之间找出卡住的那个」，两者是同一份状态的两个投影。

### 6. 「配置构建向导」改名

改为**「把这张表映射到已有本体」**。名字直接说清前提条件（本体已存在）和方向（表 → 本体），与「从表格开始引导建模」区分开。

### 7. 预演转正式执行

预演运行的报告页增加「按这次预演正式执行」。服务端按 `run_id` 保留该次运行的输入，正式执行复用，不要求用户重新上传。配置那一半由第 2 条提供，只剩数据文件需要保留。

**为什么不是「首次运行强制预演」。** 强制预演而不解决重传，是把摩擦加倍——把更贵的路变成唯一的路。

**为什么值得付存储成本。** 它同时修掉两件事：重传，以及「推荐路径比默认路径更贵」这个反向激励。数据文件的归属地是已经落地的 staging 层（`app/graphrag/etl_staging.py`），不是从零起一个新概念。

**保留策略见「待定」。**

## 未知态

第 1 条和第 3 条都依赖一个异步拿到的状态。两处都不许把「还不知道」折叠进任何一个已知态：

- 落地路由：状态未知时停在当前 `/admin`，不跳转、不空白；拿到状态再跳。
- 表格导入页首屏：状态未知时不要抢先渲染「从头配置」的形态——那会让刚走完引导的用户看到一个邀请他重做的界面然后闪一下变掉。渲染中性的加载态。

这条不是实现细节。把未知折叠进「没有映射」或「本体未确认」，等于在不知情时向用户断言一件可能是假的事——本项目已经在 `OntologySchemaPage` 的引导入口上踩过同一个坑（`readiness === null` 时不许说「这一步是安全的」）。

---

## 明确不做

- **不合并两个向导。** 它们方向相反、互补，见背景。
- **不改导航分组结构。** `model` / `ingest` / `review` 三段加两个流程外目的地（实体列表、问答诊断）的划分是对的，Foundry 的 Ontology Manager / Object Explorer 也是这么分的：分界是「定义 vs 实例」，不是流程第几步。
- **不给确认加硬闸门。** 见第 4 条。
- **不做新手教学清单。** 见 5B′。
- **不改 ETL 的删除传播语义与安全阀。** `allow_large_sweep` 默认关闭这一层不动。

---

## 待定

两个真实决定，不是实现细节，落地前需要拍板：

1. **5B′ 的价值取决于租户规模。** 个位数租户扫一眼就知道谁没配完，这条就不值得做。规模从代码里看不出来。
2. **第 7 条保留数据文件的策略。** 下次运行时清，还是 N 小时后清？有磁盘与隐私成本。默认倾向：保留到该租户下一次成功运行为止，且不跨租户共享存储路径。

## 验证

后端改动走 `python -m pytest -q`（当前基线 1694 passed）。前端有 vitest（当前基线 34 文件 336 tests），改动需要配套测试，并遵循本项目的既有实践：**每条负向断言都要故意改坏实现确认它变红**；变异不变红时先确认变异真的落进了文件。

自动化测不到、需要手工走的：从新建租户到看见第一个实体的完整链路，确认每一步都有前向出口、且没有任何一步要求重新提供系统已有的东西。
