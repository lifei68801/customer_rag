# 多跳计数的扇出陷阱检测

## 背景

2026-08-29 复查"coke-cola公司有多少个订单"这条链路时，发现系统对这个问题给出的答案 **10000 是错的**，而且是以最高置信度给出的——链路上没有任何一处察觉到异常。

正确答案是 **3353**。

### 源数据是什么样的

`soft_drink_sales.xlsx` 是一张销售事实表，10000 行，每行一笔订单：

```
Product   | Company    | Category  | ... | Order ID
Coffee    | Coca-Cola  | Coffee    | ... | 1-143-51064-X
Wine      | Coca-Cola  | Alcoholic | ... | 0-345-30366-0
Green Tea | Dr. Pepper | Tea       | ... | 1-4844-8219-0
```

实测统计：

- 10 个产品、3 家公司、10000 个订单号（全部唯一，无重复）
- 每个订单号只出现一次，因此**每笔订单恰好属于一家公司**
- 真实分布：Coca-Cola 3353 / Dr. Pepper 3330 / Pepsi 3317，合计正好 10000
- 10 个产品**各自都被 3 家公司卖过**——这是事实表的正常形态，不是数据脏

### 错误是怎么产生的

ETL 配置（`data/uploads/schema-etl/demo/*/config.yaml`）当时声明的关系是：

```
订单号 -[BELONG_TO]-> 产品   : 10000 条
产品   -[BELONG_TO]-> 公司   : 30 条  (10 产品 × 3 公司)
订单号 -----------> 公司     : 0 条 ← 不存在
```

于是"某公司有多少订单"只能走两跳 `订单号 → 产品 → 公司`。而 `产品→公司` 是多对多的，每个产品都通向全部 3 家公司，因此**每一笔订单都能走到每一家公司**。实测三家公司的两跳计数全部等于 10000。

行级信息本来直接支持 `订单号→公司` 这条边（每个 Order ID 只出现一次、只对应一家公司），是建模时把一行事实拆成两条独立的边，才丢掉了这个关联。

### 为什么整条链路都没发现

- `ontology_recall._find_multi_hop_paths()` 照常搜出了 `订单号→产品→公司`，并作为"可能相关的多跳路径"喂给深层参数生成 LLM
- `validate_structured_filter_query()` 只校验每条边是否在 `allowed_combinations` 里——这两条边确实都声明过，校验通过
- 工具返回 `matched_count: 10000`，并附上 2026-08-28 为解决"Planner 把计数误读成截断"而加的自描述 note：**"是精确完整的计数，不是上限值、也不是截断值，可以直接作为确定数字回答用户"**
- Planner 照此措辞非常肯定地回答

也就是说，为提高正确计数可信度而加的那条 note，反过来**强化了一个错误答案的可信度**。

### 更糟的是，系统在主动教模型走这条错路径

两处现存文案把这次的 bug 当成了设计意图：

`app/agent/tools/structured_filter_query/tool.py` 的 `_USAGE_GUIDE`：

> 如果 yy 和 xx 之间在候选参考的「可能相关的关系」里找不到直接的一跳关系，先检查候选参考里有没有「可能相关的多跳路径」——如果有，说明 yy 和 xx 之间隔着一个中间实体类型，**必须把那条路径的每一跳（含各自的 relation_type/direction/target_term_type）原样抄进 constraints.hops**

`app/graphrag/ontology_recall.py:343` 的注释：

> 起点和目标类型之间没有直接关系、要跨一个中间实体类型才能连起来的查询（**比如"公司有多少个订单"要经过"产品"这个中间类型**）……

这两处都是 2026-08-27 加的。当时的动机真实存在——实测 LLM 只抄第一跳、省略中间类型，导致"没有对 xx 做任何过滤、返回 yy 类型下的全部数量"。但修法用"必须原样抄"的强制语气把模型推向了另一个错误：**在计数场景下无条件信任多跳路径**。第二处注释更是直接把出问题的那个查询写成了正面示例。

## 问题的精确定义

初次描述这个问题时用的说法是"多对多边上做计数会放大"。**这个描述不够精确，照它设计会过度限制**。反例：

| 查询 | 路径 | 结果 |
|---|---|---|
| Coca-Cola 卖多少种产品 | `产品 →BELONG_TO→ 公司`（一跳） | **正确** |
| Coca-Cola 有多少个订单 | `订单号 →BELONG_TO→ 产品 →BELONG_TO→ 公司` | **错误** |

两个查询穿过同一条多对多边 `产品→公司`。所以"这条边是不是多对多"本身不构成判据。

真正的判据是维度建模里的**扇出陷阱（fan trap）**：路径 `A→B→C` 只有在 `B→C` 是函数关系（每个 B 至多对应一个 C）时，才保得住 A 对 C 的归属。`B→C` 是多对多时，路径会**凭空捏造归属**——订单本来只属于一家公司，经产品中转后变成属于三家。

由此得到可机械检查的规则：

> **计数查询里，从被计数实体出发的路径上，每一跳都必须在遍历方向上是 N:1（函数关系）。任何一跳是 N:M，这条路径就在伪造归属，计数不可信。**

这条规则不会误伤上面那个合法查询：它只有一跳，被计数实体就是 `产品` 本身，`产品→公司` 这一跳的多对多性质正是查询要表达的语义，不存在"经中转伪造归属"的问题。

## 目标

- 让系统能够识别"这次多跳计数走在扇出陷阱上"，不再把伪造出来的数字当作确定答案呈现。
- 不剥夺答案：识别出问题时优先降级措辞并给出放大倍数，而不是直接拒绝返回。
- 不引入需要人工逐条填写、且填错就失效的新声明负担。
- 修掉两处主动教模型走错路径的文案——这一项独立于检测机制本身，不做检测也要做。

## 已排除的方向：声明式基数

最初设想给 `AllowedCombination` 加一个 `cardinality` 字段（`one_to_one` / `one_to_many` / `many_to_many`），`term_type_relation_allowlist` 表加一列，在本体确认流程里让人填，路径搜索和校验读它来判断。

**排除理由：**

1. **基数是人填的，而人会填错。** 这次事故的直接原因就是 allowlist 里漏声明了 `订单号→公司` 这条边。让同一批人再去逐条标注基数，可靠性存疑；一旦有人留了默认值，检测就静默失效——而"静默失效的安全网"比没有安全网更危险，因为它会让人以为已经防住了。
2. **声明的是概念基数，执行的是数据基数。** 两者不一致时（概念上 1:N、这批数据里恰好 1:1，或者反过来）无从判断该信哪个，会引入新的争议来源。
3. **成本高。** schema 迁移 + Admin API + 本体确认流程改动 + 存量数据回填 + Neo4j/Neptune 两个后端各自适配。而且回填存量数据这件事本身就要先算出真实基数——既然都算了，不如直接用算出来的值。

保留为未来选项：如果确实出现"数据里恰好是 1:1、但概念上是 1:N，未来会变"的误判案例，再考虑用声明去**覆盖**运行时探测的结果。在此之前它是纯成本。

## 设计：运行时扇出探测

### 核心机制

不新增任何 schema。执行多跳计数时，对路径上**第一跳之后的每一跳**做一次聚合，问"这一跳的起点节点，最多能走到几个终点节点"：

```cypher
MATCH (b:Term)-[:BELONG_TO]->(c:Term)
WHERE b.tenant_id = $tenant_id AND b.type = $subject_type
  AND c.tenant_id = $tenant_id AND c.type = $object_type
WITH b, count(DISTINCT c) AS k
RETURN max(k) AS fanout
```

`fanout > 1` 即这一跳非函数，路径上存在扇出陷阱。本例中 `产品→公司` 的 `fanout = 3`。

**为什么只查第一跳之后**：第一跳是被计数实体自身的关系，它的多对多性质是查询语义的一部分（见上面那个合法查询），不构成伪造。

### 触发条件

只在**计数意图 + 多跳关系约束**同时成立时探测：

- 计数意图的信号已经存在：`args.limit == 0`（`structured_filter_query.py:602`，2026-08-28 引入的 count-only 优化）。`group_by` 分支同理需要覆盖，它也是聚合语义。
- 多跳：`RelationConstraint.hops` 长度 ≥ 2。单跳约束不触发，零额外成本。

普通的列举查询（`limit > 0`）不触发——扇出会让结果里出现重复实体，但 `count(DISTINCT o)` 和实体列表本身仍然是真实存在的关联，只是语义上"经中转推导"而非直接归属，不属于伪造数字的范畴。

### 探测结果的呈现

三个可选档位：

| 档位 | 行为 | 风险 |
|---|---|---|
| 拒绝 | 返回 `error`，让 Planner 换路径 | 没有替代路径时用户从"错答案"变成"没答案" |
| **降级 + 并报** | 照常返回 `matched_count`，把自描述 note 换成警告，并报出扇出倍数 | 依赖 LLM 读懂警告 |
| 静默降级 | 只去掉那条肯定语气的 note | 模型可能仍然肯定作答 |

**采用"降级 + 并报"。** 理由：

- 不剥夺答案。这个数字仍然是"经推导的关联数"，在没有直连边的场景下可能是用户唯一能拿到的东西。
- 报出倍数让模型有具体依据说明不确定性，而不是含糊地"可能不准"。
- "拒绝"档留给未来确实需要硬约束时再上；现阶段先观察降级档的实际服从度。

返回结构（替换现有 `limit == 0` 分支的 `note`）：

```python
{
    "matched_count": 10000,
    "fanout_warning": {
        "hop": "产品 --BELONG_TO--> 公司",
        "fanout": 3,
        "note": (
            "这条路径的第 2 跳是多对多关系（每个「产品」平均/最多关联 3 个"
            "「公司」），计数经过它中转后会把归属放大，matched_count 不是"
            "「公司」名下的真实订单数，最多可能被放大到 3 倍。回答时必须说明"
            "这个数字是经中转推导的关联数、不是精确归属计数，不要把它当作"
            "确定答案给出。"
        ),
    },
}
```

注意这里**不再出现原来那句"精确完整的计数，可以直接作为确定数字回答用户"**——两条互相矛盾的措辞同时出现会让模型无所适从。有扇出警告时只给警告；无扇出警告时保持现有 note 不变。

### 性能

- 单次探测是一个廉价聚合，走的是 `(tenant_id, type)` 复合索引 `term_tenant_term_type_idx`（`ensure_tenant_scoped_schema` 已建，见 `neo4j_client.py::_ENSURE_INDEXES_QUERIES`）。
- `limit == 0` 的计数查询本来就只有一次图查询，最坏情况（2 跳）多一次探测，翻倍。可接受。
- 探测结果只取决于 `(tenant_id, relation_type, subject_term_type, object_term_type)`，在一个租户的数据不变期内是常量，**可以进程内缓存**。ETL 写入后需要失效——先不做缓存，实测延迟不可接受时再加，避免过早引入失效逻辑的复杂度。

### 改动点

| 文件 | 改动 |
|---|---|
| `app/graphrag/neo4j_client.py` | 新增 `probe_relation_fanout(*, tenant_id, relation_type, subject_term_type, object_term_type) -> int`。参照现有 `count_relation_edges_for_term` 的形态：一个专用小聚合方法，不走通用查询接口。 |
| `app/graphrag/neptune_client.py` | 同一方法的 openCypher 实现。两个后端必须同时有，否则 `graph_backend="neptune"` 时检测静默失效。 |
| `app/graphrag/structured_filter_query.py` | `run_structured_filter_query` 在 `args.limit == 0` 且存在 `len(hops) >= 2` 的 `RelationConstraint` 时，对第 2 跳起逐跳探测；命中则改写返回结构。`group_by` 分支同理。 |
| `app/agent/tools/structured_filter_query/tool.py` | 改 `_USAGE_GUIDE` 措辞（见下节）。 |
| `app/graphrag/ontology_recall.py` | 改 `format_recall_candidates` 里那条把出问题的查询当正面示例的注释。 |

`term_guard.py::GraphClientProtocol` 不需要动——它只用 `query_subgraph`/`execute_structured_filter_query`。新方法加在具体客户端和 `structured_filter_query` 用的协议上。

## 独立子项：修掉主动引导走错路径的文案

**这一项不依赖检测机制，即使方案其余部分不做也应该做。**

`_USAGE_GUIDE` 现在用"必须原样抄进 constraints.hops"的强制语气推荐多跳路径。要改成：

- 计数场景下**优先找直连的一跳关系**；
- 只有确实不存在直连关系时才退而使用多跳路径；
- 使用多跳路径做计数时，结果是"经中转推导的关联数"，不是精确归属计数。

同时保留 2026-08-27 那次修复要解决的原始问题——"只抄第一跳、省略中间类型，等于没做过滤"——这个约束仍然成立，只是不能再用"必须"的语气把多跳路径变成计数场景的首选。

`ontology_recall.py` 那条注释里的示例要换掉：`"公司有多少个订单"` 是个反面例子，不能作为多跳路径的正面用途说明。

## 已经完成的前置修复（2026-08-29）

演示数据侧的直接修复已经做完，不在本设计的实现范围内，此处记录以免重复：

- ETL 配置补上 `订单号 -[BELONG_TO]-> 公司` 的关系映射
- `term_type_relation_allowlist` 补上对应的 `confirmed`/`draft` 声明
- 增量跑 ETL 写入 10000 条直连边

验证结果：每笔订单恰好关联 1 家公司；一跳计数 Coca-Cola 3353 / Dr. Pepper 3330 / Pepsi 3317；端到端连续 6 次查询全部返回 3353，另外两家公司交叉验证也正确。

**注意这只修好了这一份演示数据。** 任何新接入的、把事实表拆成多条边的数据源都会重新踩进同一个坑——这正是本设计要解决的问题：让系统自己发现扇出，而不是依赖每次都有人手工把直连边补对。

## 验收标准

- 对 `订单号→产品→公司` 这条路径做 `limit=0` 计数时，返回结构里出现 `fanout_warning`，`fanout == 3`，且不再出现"精确完整的计数"那句措辞。
- 对补好直连边后的 `订单号→公司` 一跳计数，返回结构不含 `fanout_warning`，现有 note 保持不变。
- 对 `Coca-Cola 卖多少种产品` 这类"被计数实体就是多对多边起点"的一跳计数，不误报。
- Neo4j 和 Neptune 两个后端的 `probe_relation_fanout` 对同一份数据给出相同结果。
- 端到端：在**没有**直连边的状态下问"Coca-Cola 有多少个订单"，模型的回答里明确出现"经推导/不是精确归属"这类限定，而不是像现在这样肯定地给出 10000。

## 不在本次范围内

- 声明式基数（见"已排除的方向"）。
- 探测结果缓存——先测实际延迟，不可接受时再单独设计失效逻辑。
- 自动**修复**扇出（比如自动推导并写入直连边）。检测和修复是两件事，自动写入图数据的风险远高于本设计，需要独立评估。
- `limit > 0` 的列举查询的扇出提示。
