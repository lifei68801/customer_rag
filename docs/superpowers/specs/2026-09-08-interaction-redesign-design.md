## 1. 问题

前台是一个孤立的问答框，用户看不出自己在问哪一份知识库；后台七个页面按三个流程组排列，
看板、数据库导入、冲突审核、数据图谱预览、报错明细五处能力完全不存在。

更具体的三个缺口，都是查证过的事实，不是推测：

1. **数字人这个概念今天已经存在，但没被看见。** 前台「还没选租户」的空态里写的是
   「租户就是知识库」（`frontend/src/pages/ChatPage.tsx`）。租户切换器藏在左下角账号块的
   下拉框里。
2. **属性值冲突今天是静默覆盖。** `upsert_term_with_node_key`
   （`app/graphrag/terms_store.py:1018-1020`）用 `ON CONFLICT (tenant_id, node_key) DO UPDATE SET`，
   表格 A 说售价 39、表格 B 说 45，后跑的赢，没有任何人知道发生过冲突。
3. **审核队列五种理由挤在一个页面。** `app/graphrag/normalization.py` 在四处
   `enqueue_for_review`，产出 `fuzzy_match_needs_confirmation` / `subject_unresolved` /
   `object_unresolved` / `not_in_confirmed_ontology` / `invalid_relation_type` 五种 reason，
   全部落进同一个「待审关系」页面、共用同一对「批准 / 驳回」按钮。而审核员面对它们时
   要做的事完全不同。

## 2. 决策台账

八条。标注「与推荐相异」的两条是用户在知悉代价后另做的选择，记录在此以免将来被误认为遗漏。

### D1 · 数字人 = 租户，租户之上加「组织」层

租户今天已经是「一整套本体 + 一整张图」——`term_types` / `terms` / 关系 / 文档 / Neo4j
节点全部按 `tenant_id` 隔离。

**换来的**：13 张业务表、`app/graphrag/neo4j_client.py` 里 168 处 `tenant_id`、21 个路由
文件一行都不用改。隔离强度就是今天的强度。

**排除的**：给 13 张表加 `domain_id` 第二隔离列。代价不是工作量，是漏掉任何一处就是
跨领域数据泄漏——这类漏在本项目今年已经出过四次。

### D2 · 引导问题：手写优先，没配就从本体兜底（与推荐相异）

推荐的是「只手写 + 保存时校验」，理由是用户分不清眼前这条是人写的还是机器拼的。
用户选了两者都要。

**消解措施（裁决）**：自动生成那一档**只用图里真有数据的类型组合**——
`Neo4jGraphClient.probe_relation_fanout(tenant_id=, relation_type=, from_term_type=,
to_term_type=, direction=)` 在没有匹配边时返回 0，拿它过滤一遍。于是两档都满足同一条
硬要求：**点了能答出来**，可信度差异不复存在。

### D3 · 数据库导入：存连接、能手动重跑，密码不入库

连接串、SQL、列映射全部入库；密码不入库，点「重新同步」时弹密码框。

**理由**：本项目所有密钥都在 `.env`，`app/config/settings.py` 里没有任何加密字段，
仓库没装任何加密库。「加密存储 + 主密钥也在 .env」并不比明文安全多少，而
「库里零密码」是可以如实向客户陈述的。

**代价**：无人值守的定时同步做不了（没人在场就没人填密码）。这是记在账上的已知限制。

### D4 · 数据审核覆盖四类

1. 现有关系队列按 reason 拆成四个分页，每页带自己的修复动作
2. 属性值冲突（新建）
3. 实体消歧（新建）
4. 脏边与孤儿数据（新建）

**明确不做**：低置信度审核。抽取环节今天不产出任何置信度分数
（`app/graphrag/normalization.py` 里 grep `confidence` 无结果），要做得先改抽取。

### D5 · 看板全部实时算（与推荐相异）

推荐的是快照 + 标注「统计于何时」。用户选了实时。

**消解措施（裁决，两条，均在「实时」内部）**：

1. 边计数**从节点侧发起**：`MATCH (t:Term {tenant_id: $tenant_id})-[r]->() RETURN count(r)`,
   走已有的 `term_tenant_node_key_idx`（`neo4j_client.py:482`），不是全库扫关系；
   只数出边，避免一条边数两次。
2. 每个领域一张卡、**各自独立请求、各自落位**，先出骨架屏，不等最慢的那个领域。

### D6 · 图谱预览 = 以实体为中心的邻域图

1–2 跳，上限 300 节点。后端 `query_subgraph` 已就绪，前端 `sigma` + `graphology` +
`graphology-layout-forceatlas2` 已在 `frontend/package.json`。

**硬要求**：超过上限时必须写出「已截断，画了 300 / 1013」，不是默默少画。

### D7 · 报错明细只收「用户能看懂、能纠正」的失败

三个来源：文档摄取失败、ETL 跳过的行、问答未命中。每条带一个修复动作。

**明确不做**：通用异常收集器（500 / LLM 超时 / Neo4j 断连）。理由不是工作量——那种表
本身就是个静默失败：写入点漏一处就永远看不见，而用户会把「报错明细是空的」读成「没出错」。

### D8 · 实体明细归入「结果预览」，孤儿组「明细查询」消失

`frontend/src/adminRoutes.ts` 里援引 Foundry 的论证（Ontology Manager 管定义、
Object Explorer 查实例）反对的是把实体明细塞进**流程**末尾。「结果预览」本身不是流程的
一步，它就是 Object Explorer，因此不冲突。

### 裁决补充（未单独提问）

- **看板只显示这个账号有权访问的领域。** 聚合数字也是信息：给 member 看到他无权访问的
  领域有多少实体，等于泄露业务规模。
- **一个会话属于一个数字人。** `chat_sessions` 主键 `(tenant_id, session_id)`
  （`app/memory/schema.py:62-70`）今天就是这个语义，左栏跟着右栏切是免费的。
- **组织管理页只有 admin 能进**，跟现有租户管理页同一档，入口在账号菜单不在侧边栏。
- **引导建模**（现有 `GuidedOntologyPage`，今天无导航入口）随「本体创建」模块浮上来。

## 3. 数据模型

只动两处：租户之上加一层组织，账号与租户之间加一张多对多。**隔离维度仍然是一维。**

```
organizations            ← 新表
  org_id: muji
  name:   无印良品

tenants                  ← 加一列 org_id
  muji-商品    org_id=muji   ← 数字人「导购小美」
  muji-门店    org_id=muji   ← 数字人「店务老张」
  muji-供应链  org_id=muji   ← 数字人「采购老王」

user_tenants             ← 新表（多对多）
  alice → muji-商品
  alice → muji-门店
  bob   → muji-供应链

tenant_personas          ← 新表（数字人的脸）
  muji-商品 → 头像 / 人设一句话 / 引导问题 ×3–6

terms / term_edits / …   ← 一行都不改，依旧 WHERE tenant_id = ?
```

### 新表清单

| 表 | 为了什么 | 关键列 |
|---|---|---|
| `organizations` | 把多个领域归到一个客户名下 | `org_id` · `name` · `status` |
| `user_tenants` | 一个人能看几个数字人 | `username` · `tenant_id` |
| `tenant_personas` | 数字人的头像 / 人设 / 引导问题 | `tenant_id` · `avatar` · `tagline` · `questions` |
| `db_sources` | 数据库导入的连接与映射（**无密码**） | `tenant_id` · `source_id` · `driver` · `host` · `port` · `database` · `username` · `query` · `mapping` |
| `attribute_conflicts` | 属性值冲突，不再静默覆盖 | `tenant_id` · `node_key` · `field` · `values` · `status` |

### 加列（非建表）

- `tenants.org_id TEXT`（可空——存量租户不属于任何组织）
- `qa_diagnostics.outcome TEXT NOT NULL DEFAULT 'answered'`
  （今天答不出来和答得好长得一模一样）

### 授权面（本设计最危险的地方）

`session.tenant_id` 作为**授权判据**今天只有两处，逻辑完全相同：

- `app/api/deps.py:449-451`（`require_tenant_access`，注释称其为「整个账号体系唯一真正的
  安全边界」）
- `app/api/admin_auth_routes.py:188`（切换当前租户）

另有两处只是日志（`admin_terms_routes.py:325`、`:932`），不是判据。

`user_tenants` 上线后，这两处必须收敛成**同一个函数**。两处各改各的，就是下一个越权洞。

## 4. 前台

左栏（`frontend/src/components/ChatSidebar.tsx`）和中栏
（`frontend/src/components/ChatWindow.tsx`）今天已有。新增的只有两样：

```
┌──────────┬────────────────────────┬────────────┐
│ 会话历史  │ 你好，我是导购小美       │ 数字人      │
│          │ 我知道商品、口味、       │ ● 导购小美  │
│ ▪▪▪▪▪▪   │ 产地和类目             │ ○ 店务老张  │
│ ▪▪▪▪     │                        │ ○ 采购老王  │
│ ▪▪▪▪▪    │ (有哪些无香料的洗发水?) │            │
│ ▪▪▪      │ (这个月新上了什么?)     │ 只列这个    │
│          │ (Beer 是哪个产地的?)    │ 账号有权   │
│ 随右栏切换│                        │ 访问的     │
│ 只列当前  │ ┌────────────────────┐ │            │
│ 数字人的  │ │ 问点什么…          │ │            │
└──────────┴────────────────────────┴────────────┘
```

右栏不是新概念——它是把已经存在的租户切换器从下拉框升级成常驻栏。

### 引导问题的两条硬规矩

1. **点了必须能答出来。** 手写那批保存时真跑一遍实体匹配，答不出来不让保存；
   自动生成那批只用 `probe_relation_fanout` 报告有边的类型组合。
2. **失效了必须有人知道。** 本体改动导致某条手写问题不再命中时，它不是默默消失，
   而是在看板上变成一条待办。

## 6. 审核的四张脸

| 分页 | 后端 reason | 审核员要做的事 | 页面上的动作 |
|---|---|---|---|
| 待确认匹配 | `fuzzy_match_needs_confirmation` | 这个名字是不是那个实体 | 确认建议名 / 换一个 / 驳回 |
| 一端对不上 | `subject_unresolved` `object_unresolved` | 新建或指定一个实体 | **就地新建实体**，然后批准 |
| 超出本体范围 | `not_in_confirmed_ontology` | 要不要放宽本体 | **就地加白名单组合**，然后批准 |
| 关系类型不合法 | `invalid_relation_type` | 改关系类型名 | 选一个已确认类型 / 驳回 |

### 属性值冲突

改法：在覆盖前比对，值不同就记一条冲突，**并且保留先写的值不动**——不确定的时候不擅自
改数据。冲突页列：实体 · 属性 · 值 A（来自 `商品表.xlsx` 第 88 行）· 值 B（来自
`价格库.csv` 第 12 行），三个动作：选 A、选 B、手填。`terms.source` 这一列今天就在。

## 8. Global Constraints（所有阶段共同遵守）

以下每一条都对应仓库里已经存在的约定或已经付过代价的教训，实施时逐字照办。

1. **不许静默失败。** 判据是「猜错时用户能不能看见并纠正」。拿不到数据就报错，
   不要退回一个看起来正常的默认值。
2. **注释里不许写未经验证的因果。** 本仓库已有两处守卫被查出建立在虚假理由上。
   写「因为 X 所以 Y」之前先验证 X。
3. **测试不许假绿。** 每个断言都要问：这条断言在错误实现下会不会也通过？
   同一个批次里必须同时包含成功和失败的样本。
4. **变异必须真的改变行为。** 变异脚本必须先断言锚点找到了、且文件内容确实变了。
5. **绝不使用 `git add -A` 或 `git add .`**，必须逐个文件点名。工作区里有用户自己保留的
   未提交改动。
6. **不推送到 origin**，推送需要用户单独指示。
7. **不修改用户的 `.env`**，不动 `data/` 下的真实数据库。
8. **租户隔离是二元的**：一处漏过滤就是泄漏。新增的每个查询都必须带 `tenant_id` 条件，
   新增的每个路由都必须走 `deps.require_tenant_access`。
9. **后端测试**：`.venv/Scripts/python.exe -m pytest -q -p no:cacheprovider`。
   全量约 78 秒 1893 条。**不要用 `| tail`**——git-bash 下管道会导致输出缓冲死锁，
   看起来像卡住；重定向到文件再读。
10. **前端测试**：`cd frontend && npx vitest run src/admin` 与 `npx tsc --noEmit`。
11. **一次只跑一个 pytest 进程。** 两个并发会互相争用并双双超时。
12. **改了后端路由必须重启后端**，否则前端撞 404/405。
