# 本体建模：三种构建方式合到一个页面

日期：2026-09-17。承接 `2026-09-16-ontology-modeling-workbench-design.md`（模板构建）与既有的「本体结构」页（手动构建），新增「智能创建」。

## 背景

今天侧边栏「本体创建」组里，**本体结构**（手工逐条增删实体类型/关系类型/约束）和**建模工作台**（选内置领域模板起步、对齐数据表、应用到草稿）是两个平级入口。用户看不出它们是同一件事的两种做法——都是"把这个租户的本体建出来"，终点都是同一份**草稿**。而对完全不知道从哪开始、手上也没有现成数据表的客户，两条路都不好走：模板未必覆盖他的领域，手工要求他先想清楚。

## 目标

1. 侧边栏「本体创建」下第一项是**本体建模**，一个页面，页内三个 tab：**模板构建** / **手动构建** / **智能创建**。
2. 模板构建 = 现在的建模工作台整套（工作区、数据对齐、落地状态、应用 diff、导出 skill），原样搬进 tab，不改行为。
3. 手动构建 = 现在的本体结构整套（三个子 tab：实体类型 / 关系类型 / 约束，加"确认本体"），原样搬进 tab，不改行为。
4. 智能创建 = 新功能，两段式：
   - **访谈**：LLM 连续提问（你们做什么生意、最关心什么、有哪些角色/单据），用户逐轮回答，右侧骨架实时长出候选实体/关系，每条标明"这是猜的"和它出自哪一轮回答。
   - **问题清单**：用户录入若干真实业务问题，系统反推每个问题需要哪些实体/关系，标出骨架里缺的；这份清单同时是验收用例（本体确认后可以拿去问答里跑一遍）。
5. 三者**各自独立**：不共享状态，各自把结果写进同一份**草稿**。

## 非目标

- 不合并三者的内部状态（模板构建的工作区不给智能创建用，反之亦然）。
- 不做"访谈过程跨会话续接"之外的协作（多人同时访谈不做冲突合并）。
- 不改「本体图」「数字人」的位置。
- 不改本体确认（confirm）的语义与前置条件。

## 导航与页面

侧边栏「本体创建」组变成：**本体建模** / 本体图 / 数字人。

- 新路由键 `ontologyModeling: '/admin/ontology/modeling'`。
- 页内 tab 用 URL 查询参数 `?way=template|manual|smart` 记住（缺省 `manual`——今天绝大多数租户是在手工维护已有本体，首屏不该把他们扔进一个空工作区）。
- 旧路径保留为重定向：`/admin/ontology/ontology` → `/admin/ontology/modeling?way=manual`，`/admin/ontology/guided` → `/admin/ontology/modeling?way=template`。两条都进 `LEGACY_REDIRECTS`（收藏夹、文档里的旧链接不能断）。
- 草稿/已确认切换器只在**手动构建** tab 显示（另两个 tab 产出的是"将要写进草稿的东西"，没有"看已确认版"这个轴）。本体图页保留自己那个。

## 智能创建的数据模型

新表 `ontology_interview_sessions`，一个租户一份（与建模工作区同样的"长期存在、可续"取向）：

```sql
CREATE TABLE IF NOT EXISTS ontology_interview_sessions (
    tenant_id   TEXT NOT NULL PRIMARY KEY,
    state_json  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    updated_by  TEXT NOT NULL
);
```

`state_json`：

```jsonc
{
  "turns": [
    { "role": "assistant", "text": "你们主要做什么生意？", "at": "..." },
    { "role": "user", "text": "我们是做消费品零售的，主要卖服装和家居", "at": "..." }
  ],
  "skeleton": {
    "term_types": [
      { "value": "商品", "display_name": "商品", "confidence": "guess",
        "from_turn": 1, "rationale": "用户说主要卖服装和家居，商品是最小的售卖单位",
        "extra_fields": [{ "name": "price", "value_type": "number", "label": "价格" }],
        "review": "pending" }
    ],
    "relation_types": [{ "relation_type": "SOLD_AT", "example_phrase": "某商品在某门店有售",
                         "confidence": "guess", "from_turn": 1, "rationale": "…", "review": "pending" }],
    "constraints": [{ "subject": "商品", "relation": "SOLD_AT", "object": "门店",
                      "confidence": "guess", "from_turn": 1, "review": "pending" }]
  },
  "questions": [
    { "text": "哪个品类上个月销量最高？", "needs": { "term_types": ["品类", "商品"], "relation_types": [] },
      "missing": ["品类"], "at": "..." }
  ],
  "done": false
}
```

- `confidence` 只有 `guess` 一个取值——**全都是猜的**。留这个字段是为了将来能区分"用户明确说过的"与"LLM 推的"，v1 界面上一律显示"这是猜的"。
- `rationale` 必填：一条用户没说过的实体凭空出现而不给理由，用户没法判断该不该留。
- `from_turn` 是 `turns` 的下标，界面上点一下能跳回那一轮对话。
- `review` 与模板构建同一套取值（`pending` / `accepted` / `rejected`），但**不共用存储**。

本体三张表一列不加。

## 智能创建的行为规格

### 1. 访谈

- 首轮由后端生成开场问题（不调 LLM，固定一句："先说说你们主要做什么生意？"——第一问不该花一次 LLM 调用，也不该有猜错的余地）。
- 用户每回答一轮，后端把**全部历史轮次 + 当前骨架**交给 LLM，要求返回一个 JSON：`{"question": "下一个问题", "add": {"term_types": […], "relation_types": […], "constraints": […]}, "done": false}`。
- LLM 返回的每个元素必须带 `rationale`；没带的丢弃（不编理由替它圆场）。
- 元素名与既有校验规则对齐：关系类型名必须匹配 `^[A-Z][A-Z0-9_]{0,63}$`，字段名匹配 `^[a-zA-Z_][a-zA-Z0-9_]{0,63}$`，`value_type` 必须在 `EXTRA_FIELD_VALUE_TYPES` 里。不合规的那一条丢弃，其余保留（一条脏数据不该让整轮白问）。
- 与既有骨架**重名**的元素：不重复添加，但把新的 `rationale` 追加到已有那条上（同一个概念被两轮回答佐证，是加强不是冲突）。
- LLM 超时/异常/返回非 JSON：这一轮不加任何元素，界面上说明"这一轮没能从回答里认出新概念，可以换个说法再说一次"，**不静默**。超时上限 60 秒（访谈是同步等待的交互，比抽取那条 30 秒的路径宽松，但不能无限等）。
- `done: true` 或用户点"结束访谈"时停止提问；骨架仍可继续审阅。

### 2. 问题清单

- 用户逐条录入业务问题。每录入一条，后端把问题 + 当前骨架交给 LLM，要求返回 `{"needs": {"term_types": […], "relation_types": […]}}`。
- `missing` 由后端计算：`needs` 里不在骨架（`review != 'rejected'`）中的名字。不让 LLM 自己报缺什么——它看不到 review 状态，也容易顺着问题编。
- 缺的元素在界面上一键加进骨架（`confidence: 'guess'`、`rationale` 写"来自问题：…"）。
- 问题清单只存不跑：v1 不接问答验收（拿它去问答里跑一遍是后续的事），但文案要说清"确认本体后可以拿这些问题去问答页验收"。

### 3. 写入草稿

- 只写 `review === 'accepted'` 的元素，投影规则与模板构建一致（约束的主/宾/关系三者都 accepted 才带上）。
- 写入前必须先看 diff（复用既有 `apply-preview` 端点），有删除项弹确认框——理由与模板构建相同：`draft/replace` 是整份替换，会删掉用户在手动构建里加的东西。
- 写入走既有 `POST /api/admin/ontology/{tenant_id}/draft/replace`，不新增写草稿的端点。
- 智能创建**不产出 ETL 映射**（它没接触过任何数据表），`etl_mapping` 传 null（`replace_draft` 对 null 的语义是"这次不改映射"）。

## 接口

全部挂在 `tenant_scoped` 下，prefix 沿用 `/api/admin/ontology`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/{tenant_id}/interview` | 读访谈会话；不存在返回 `{"session": null}` |
| POST | `/{tenant_id}/interview` | 建会话，返回开场问题 |
| POST | `/{tenant_id}/interview/answer` | body `{answer, updated_at}`，调 LLM，返回新一轮问题与新增元素；乐观锁同工作区 |
| PUT | `/{tenant_id}/interview` | 整份写回 state（审阅决定、手工改名走这条）；乐观锁 |
| DELETE | `/{tenant_id}/interview` | 重新开始 |
| POST | `/{tenant_id}/interview/questions` | body `{text, updated_at}`，调 LLM 反推 needs，算 missing，追加进 questions |

`apply-preview` / `draft/replace` 复用既有端点。

## 决策记录

| # | 决定 | 备选 | 为什么 |
|---|---|---|---|
| 1 | 一个页面三个 tab | 侧边栏加第三层 / 三个平级页 | 三者是同一件事的三种做法；侧边栏两层结构不动（用户选） |
| 2 | 三者不共享状态 | 共用一份工作区 | 用户选。代价：同一个概念在两个 tab 里各建一次没人提示 |
| 3 | 缺省 tab 是手动构建 | 模板构建 | 今天多数租户在维护已有本体，首屏不该把他们扔进空工作区 |
| 4 | 访谈第一问写死 | 也交给 LLM | 省一次调用，且第一问没有猜错的空间 |
| 5 | 每个元素必须带 rationale | 只给名字 | 凭空出现的实体用户没法判断去留 |
| 6 | missing 由后端算 | LLM 自报 | LLM 看不到 review 状态，且容易顺着问题编 |
| 7 | 问题清单只存不跑 | 直接接问答验收 | 验收要跑完整问答链路，是另一条线；v1 先把清单攒下来 |
| 8 | 智能创建不产出 ETL 映射 | 猜一份 | 它没接触过数据表，猜出来的映射一跑就错 |
| 9 | 访谈超时 60 秒 | 沿用抽取的 30 秒 | 访谈是同步交互，用户在等；但不能无限等 |
| 10 | 版本切换器只在手动构建 tab | 三个 tab 都有 | 另两个 tab 产出的是"将要写进草稿的"，没有已确认版这个轴 |

## 风险

- 三者独立意味着同一个概念可能在模板构建的工作区和智能创建的骨架里各存一份，写草稿时后写的覆盖先写的（`draft/replace` 是整份替换）。写入前的 diff 会把这件事显示出来（"会删掉 X"），但用户要自己看懂。
- LLM 访谈的质量完全取决于模型：问得不好、猜得离谱都会发生。缓解只有两条——每条都标"这是猜的"+ 给理由，以及写入前必须审阅。
- 页面变大：三个 tab 各自的代码量都不小，`ModelingPage` 只做 tab 切换与路由参数，三套内容各自保持独立文件。

## 增补（2026-09-17，用户重新定位三者关系）

**三种方式只是初始化本体的三条思路，终点是同一个可编辑的本体结构。** 初始化之后，用户在结构里核实、增删改，再存草稿或确认。

### 变更

1. **tab 改名与顺序**：模板构建 / 智能创建 / **本体结构（核实与修改）**。原「手动构建」改名为「本体结构」——它不再是并列的第三种思路，而是所有路的终点。顺序即流程：两种初始化 → 核实修改。
   - URL 参数值 `?way=manual` **不变**（改值会让已发出去的链接失效）；只改标签与顺序。
2. **写入草稿后自动跳转**：模板构建、智能创建写入草稿成功后，自动切到「本体结构」tab，并在顶部显示一条提示：刚写入了多少个实体类型 / 关系类型 / 约束，请核实。停在生成器里的话，用户不知道下一步去哪。
3. **生成器里的接受/拒绝保留**：本体三张表不存"来源"和"理由"（决策 9 不加列），一旦写进草稿，"这是猜的""出自第几轮回答"就全丢了。先在生成器里带着理由筛一遍，再到结构里改——两段各有各的信息。
