# 前端体验 Demo 设计方案

> 状态：设计定稿（经 grill-me 逐项确认）
> 背景：用户希望基于当前后端（Agent 推理核心 + GraphRAG + 检索层，本次会话前面 4 个子项目已经加固过安全/模糊匹配能力）搭建一个可交互的前端 demo，放在 `frontend/` 文件夹下，让人能实际体验这套系统的问答能力。视觉设计和交互参考产品网站 `raft.build`（用户最初提到的"slock.ai"域名已重定向到这个产品，经确认就是它）。
>
> 本设计经由 `superpowers:grill-me` 逐项提问确认，跳过了常规 brainstorming 流程的重复提问阶段（grill-me 已经覆盖同等深度的澄清），但仍按项目既定规范产出设计文档留痕，后续走 `writing-plans` → Subagent-Driven Development 实现。

## 1. 设计参照来源

`https://raft.build/zh-cn/`（多智能体协作平台"Raft"的中文站）。通过 WebFetch 抓取分析得到的设计基调（注意：以下是从渲染后页面文本/结构推断的近似值，不是精确抓取的 CSS 变量，实现时作为方向参考，允许在此基础上做工程判断上的微调）：

- **配色**：深色背景（近黑 `#0A0A0A` ~ 深灰 `#0F0F0F` 一档）；卡片/容器背景略浅于底色（`#1A1A2E` ~ `#1F1F2E` 一档），形成分层感；主文字近白（`#F5F5F5`）；次要文字中灰（`#9CA3AF` 一档）；品牌强调色为青蓝色系（`#0EA5E9` ~ `#06B6D4` 一档）；边框极淡灰（`#404050` 一档），少量使用；状态色（如成功）用绿色（`#10B981` 一档）。
- **字体**：现代几何无衬线字体（Inter 一类），标题字重较粗（600-700）与正文常规字重（400）形成明显层级对比，字号档位从大标题到小字说明有 4-5 档；行高偏宽松（约 1.6-1.8 倍）。
- **布局**：宽松留白、呼吸感强，非信息密集型；卡片式模块；小到中等圆角（4-12px 一档）；阴影极淡或不用，不做重投影；导航栏固定顶部，可能带轻微半透明/毛玻璃效果。
- **整体调性**：极简专业、科技冷静、克制不浮夸——不是霓虹赛博风，是"安静的科技感"。

## 2. 功能范围

**做**：
- `/agent/chat` 的文字流式问答（SSE），消费 `delta`（逐句流式文本）和 `final`（含 `text`、`used_sources`）两类事件，`audio` 事件类型忽略（本次不做语音）。
- 回答下方展示来源引用（`used_sources` 里的文档片段 ID 列表），作为"这条回答参考了哪些资料"的直观体现。
- 多轮对话：前端在页面加载时生成一个稳定的 `session_id`（如 `crypto.randomUUID()`），后续同一浏览器标签页内的所有消息复用同一个 `session_id` 和固定的 `user_id`（如 `"demo-user"`），让后端的会话记忆/指代消解/纠错入口等能力在多轮对话里生效。

**不做**（已在 grill-me 中确认排除）：
- 语音输入/输出（ASR 流式采集、TTS 播放）——工程量大（麦克风权限、音频编码、WebSocket 双工），且不是本次"展示 RAG/Agent 推理能力"的关键路径。
- `/qa` 端点——功能上是 `/agent/chat` 的子集，不重复做一遍 UI。
- "幕后过程"诊断面板（TermGuard 命中/安全拦截/检索分数等）——现有 `/agent/chat` 的 SSE 事件不携带这些字段，做这个面板需要改动 `app/api/agent_routes.py` 的 `final` 事件结构，突破"改动只留在 `frontend/` 文件夹"这条原则，且本次目标是"体验"而非"给开发者看内部状态"。
- 多租户切换器——`tenant_id` 前端硬编码为固定值（见第 5 节），不做租户选择 UI。
- 完整营销落地页结构（定价/用户证言/企业背书墙/FAQ 板块）——只保留轻量 Hero 说明区，见第 6 节。

## 3. 技术栈与项目结构

**React + Vite + TypeScript + Tailwind CSS**，全部产物落在 `frontend/` 目录下，与后端 Python 代码完全隔离，互不影响构建/依赖体系。

```
frontend/
├── index.html
├── package.json
├── vite.config.ts          # 含开发代理配置，见第 4 节
├── tailwind.config.ts       # 深色系配色 token（对应第 1 节配色方案）
├── tsconfig.json
└── src/
    ├── main.tsx
    ├── App.tsx
    ├── components/
    │   ├── Hero.tsx          # 轻量说明区
    │   ├── ChatWindow.tsx    # 消息列表容器
    │   ├── MessageBubble.tsx # 单条消息气泡（用户/助手两种样式）
    │   ├── SourceCitations.tsx  # used_sources 引用列表
    │   └── ChatInput.tsx     # 输入框+发送按钮
    ├── hooks/
    │   └── useAgentChat.ts   # 封装 SSE 连接、消息状态管理、session_id 生成
    ├── lib/
    │   └── sse.ts            # 解析 text/event-stream 响应的通用工具
    └── styles/
        └── index.css         # Tailwind 入口 + 全局样式
```

## 4. 前后端联调方式

**Vite 开发代理**，不改动后端任何代码：

```ts
// vite.config.ts（示意）
export default defineConfig({
  server: {
    proxy: {
      '/agent': 'http://localhost:8000',
      '/health': 'http://localhost:8000',
    },
  },
})
```

浏览器只与 Vite 开发服务器（默认 `localhost:5173`）交互，Vite 把 `/agent/chat` 等路径转发到本地 FastAPI（`localhost:8000`）。SSE（`text/event-stream`）响应经 Vite 代理可以正常流式透传，不需要额外配置。

运行方式：两个独立进程——`uvicorn app.main:app --reload`（后端）+ `npm run dev`（前端，在 `frontend/` 目录下）。

## 5. 租户与会话身份

- `tenant_id` 前端硬编码为常量 `"demo"`，每次请求都带上；后端 `gateway_shared_secret` 未配置时（本地开发默认），`resolve_tenant_id()` 会走请求体兜底路径信任这个值（见 `app/api/deps.py::resolve_tenant_id`）。
- `session_id`：页面加载时用 `crypto.randomUUID()` 生成一次，存入组件状态（不需要持久化到 `localStorage`，刷新页面开新会话是可接受的行为）。
- `user_id`：硬编码为 `"demo-user"`。

## 6. 页面结构

单页应用，从上到下：

1. **顶部导航栏**：固定顶部，左侧 Logo/系统名称（如"客服智能问答 Demo"），右侧可放一个静态的"关于"链接或留空——不需要复杂导航项，因为没有多页面路由需求。
2. **Hero 说明区**：一句话标题说明"这是什么"（如"基于知识图谱增强的企业客服问答 Agent"）+ 一句副标题简述系统能力（检索增强、术语图谱、多轮记忆），视觉上参照 raft.build 首屏的留白和字号对比，但内容大幅精简（不需要双 CTA 按钮、不需要背景动画视频等重元素）。
3. **聊天界面主体**：占据页面主要空间的对话窗口——消息列表（用户消息右对齐/助手消息左对齐，气泡样式区分）+ 底部固定输入框。这是整个 demo 的核心交互区，需要投入最多设计打磨（流式文字逐字/逐句出现的视觉效果、加载态、来源引用卡片样式）。

不做：定价表、用户证言轮播、企业 Logo 墙、FAQ 手风琴、页脚多栏链接——这些是纯营销内容，与"体验系统能力"这个目的无关。

## 7. 交互细节

- **流式文字显示**：收到 `delta` 事件时，把 `text` 追加到当前助手消息气泡的末尾（不是逐字符打字机效果，是按句子边界一次性追加一段——这是后端 SSE 事件本身的粒度，`delta.text` 每次就是一整句）。
- **来源引用**：收到 `final` 事件后，若 `used_sources` 非空，在该条助手消息气泡下方渲染一个小的引用列表（如 `📄 faq/login-reset.md`），点击不需要有实际跳转行为（demo 语料没有可访问的原文链接）。
- **加载态**：用户发送问题后到第一个 `delta`/`final` 事件到达之间，助手消息位置显示一个轻量的"思考中"指示（如三个跳动的点），不做骨架屏这类重量级 loading。
- **错误处理**：SSE 连接失败或后端返回非 200 时，在聊天流里插入一条系统提示消息（如"连接后端失败，请确认服务已启动"），不用 alert/modal 打断体验。
- **深色模式**：只做深色主题（对应 raft.build 的深色系设计基调），不做浅色模式切换开关——减少设计和实现的范围，这次目标不是做一个通用可配置的设计系统。

## 8. 示例演示数据

后端目前没有任何真实摄取的文档语料（`app/graphrag/terminology_seed.yaml` 也只是占位数据），demo 打开后问任何问题都会因为检索不到内容而走 Fallback 兜底转人工。为了让 demo 有真实可问的内容：

- 新增一份小型示例 FAQ 语料（5-8 条，Markdown 格式，每条一个独立文件或合并成一个结构化文档，具体由实施阶段的任务规划决定），延续仓库已有的"示例XX"占位命名风格（不编虚构品牌名），覆盖典型企业 SaaS 客服场景：
  - 登录失败/密码重置
  - 示例错误码含义与处理步骤（复用 `terminology_seed.yaml` 已有的"示例错误码E502"/"网关超时示例"，让 TermGuard 术语强制注入在 demo 里能真实触发一次，直观体现 GraphRAG 能力）
  - 订阅/账单相关问题
  - 网络连接问题
  - 示例登录模块相关的功能说明
- 语料文件放在 `frontend/` 之外（如 `docs/demo-data/`），不算前端范围，但是让前端"有意义地可用"的必要前提，本次一并准备。
- 用现有摄取脚本导入：`python -m app.ingestion.main --dir docs/demo-data --tenant-id demo --build-graph`（`--build-graph` 触发 LLM 关系抽取 + 术语归一化 + 写入 Neo4j，让图谱侧的能力也能在 demo 里体现；`--tenant-id demo` 与第 5 节前端硬编码的 `tenant_id` 保持一致）。
- 不新增/修改 `terminology_seed.yaml` 本身的结构，只复用其中已有的术语条目让示例语料与术语表对得上。

## 9. 测试与验证方式

前端本身不引入自动化测试框架（demo 性质，不是要长期维护的生产代码库，且用户体验类的视觉/交互细节更适合人工核验而非快照测试）。验证方式：

- 实施阶段用 `run` 技能（或手动）启动后端 + 前端两个进程，浏览器实际打开页面验证：Hero 区渲染、发送消息后流式文字正确显示、来源引用正确展示、多轮对话（提问一个模糊指代问题验证记忆/澄清链路）、错误态（故意断开后端验证提示文案）。
- 示例语料摄取后，用 `python -m app.graphrag.review_cli list` 确认没有大量候选关系堆积在人工审核队列（如果堆积严重说明语料和术语表对不上，需要调整语料内容）。

## 10. 范围之外（不做）

- 语音输入/输出。
- `/qa` 端点接入。
- 幕后诊断面板（需要改动后端 SSE 事件结构）。
- 多租户切换 UI。
- 完整营销落地页板块（定价/证言/企业墙/FAQ）。
- 浅色模式切换。
- 前端自动化测试框架。
- 生产部署配置（Docker 化前端、CORS 中间件、反向代理配置等）——本次只做本地开发体验 demo。
