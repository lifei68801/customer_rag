# 知识图谱本体 Schema 设计

> 状态：设计定稿（经三轮用户 grill-me 逐题确认，纯设计文档，本次不落地任何代码）
> 版本历史：
> - 第一轮：节点分类（term_type/product_line）枚举化，关系类型维持代码固定不可编辑，
>   domain/range 做统计自举的软约束。
> - 第二轮：追加关系类型的"租户级自定义"能力（草稿+工程审核），domain/range 改为
>   "专家声明表 + 统计数据"双来源合并判定。
> - 第三轮（本版本，替换第二轮的相关结论）：整体模型改为**抽取前必须先定义并图形化确认
>   本体 schema**——分类、关系、属性、约束四个维度都以默认参考数据打底，业务可自由增删改，
>   确认后才允许对应租户的图谱抽取继续进行。domain/range 从软约束改为硬约束（不在已确认
>   schema 里的组合转人工审核，不自动写入）。关系类型不再区分"全局固定"和"租户自定义"
>   两层，统一成单一租户表，10 种默认值只是初始种子，可删可改。新增属性层设计（之前两轮
>   都明确排除，本轮加入）。新增"孤点数据保护"专章，覆盖 schema 编辑对已有数据的影响。

## 1. 现状与复用点

- `app/graphrag/terms_store.py`：术语（节点）表，全局不分租户，业务后台可在线增删改。
- `app/graphrag/neo4j_client.py::_ALLOWED_RELATION_TYPES`：本轮之前是 10 种全局固定关系
  类型的白名单，本轮改造为租户级可编辑表（见第 4 节），10 种作为初始种子迁移进去。
- `app/ingestion/pipeline.py`：`_embed_and_upsert`（向量化写入）和
  `_maybe_extract_graph_relations`（图谱关系抽取）是两条独立的异步路径，只有后者受
  `build_graph` 参数控制——这是本轮"门禁只挡图谱抽取、不挡向量化"的技术前提。
- `app/graphrag/normalization.py::normalize_and_write_relations`：候选关系两侧对齐术语表
  后，`relation_type` 不合法（`invalid_relation_type`）或两侧未对齐，都会转入
  `review_queue.py` 人工审核队列，而不是直接丢弃——本轮 domain/range 硬约束复用这个既有
  分流机制，增加一个新的拒绝原因。
- Neo4j 关系类型（edge type）一旦写入**不可原地修改**——"改名"一个已存在类型的边，只能
  新建新类型边、复制属性、删旧边，是一次真正的数据迁移，不是字符串替换。这个技术约束
  直接决定了第 4.4 节的设计。

## 2. 强制 Schema-First 门禁

**结论：抽取前必须先定义并确认本体 schema，按租户隔离，只挡图谱抽取，不挡向量化。**

- **按租户隔离**：每个租户的本体、每个租户自己确认，不影响其他租户。
- **只挡图谱抽取，不挡向量化**：门禁检查点在
  `app/ingestion/pipeline.py::_maybe_extract_graph_relations` 调用前，检查该租户的本体是否
  已确认（`ontology_status == 'confirmed'`）；`_embed_and_upsert`（向量化，RAG 检索的基础）
  不受影响，无条件执行——不能因为本体还没定义好就连文档上传/向量化都一起卡住。
- **草稿/已确认两态生命周期**：本体永远处于两个版本之一——
  - `confirmed` 版本：图谱抽取实际读取、生效的版本。
  - `draft` 版本：业务正在编辑的工作副本，随时可以修改保存，**不影响正在进行或已完成的
    抽取**（抽取用的始终是当前 `confirmed` 版本）。
  - 编辑 `draft` 不会立即生效；业务在图形化确认界面里点击"确认"时，`draft` 才会替换成
    新的 `confirmed` 版本。首次确认之前，该租户没有 `confirmed` 版本，图谱抽取门禁保持
    关闭。
- **图形化确认界面**：确认前，业务能直观看到即将生效的完整 schema——分类列表、关系类型
  列表（含例句、是否允许链式查询）、每个分类的属性字段、domain/range 允许组合——而不是
  盯着表单逐行核对。这个界面本身就是安全网，取代了下面第 4 节里原本设想的工程师人工审核
  关卡。

## 3. 节点分类层（term_type / product_line）——沿用第一轮结论，未修改

- 两条独立分类轴，都从自由文本收成受控枚举，扁平结构，不做父子层级。
- 硬约束：`terms` 表提交时 `term_type`/`product_line` 必须命中枚举表。
- 枚举值默认给参考示例（如"产品/功能、地点/设施、角色/职位……"），业务可自由增删改，与
  本轮"分类/关系/属性/约束都给默认参考、用户可增删改"的整体原则一致——这一层从第一轮起
  就已经是这个模型，不需要改动。
- **删除保护维持不变**：删除一个已被术语引用的枚举值时拒绝（需先把引用它的术语改到其他
  类型）——这里和第 4.4 节"关系类型允许直接删除"的处理不同，原因见第 5 节"孤点数据保护
  规则"的说明：`term_type` 是 `terms` 表的硬约束外键，删除在用的枚举值会让已有术语行变成
  无效数据；关系类型不是任何表的外键约束对象，删除不会破坏任何行的结构有效性，两者的
  风险性质不同，不能类比处理。
- 改名允许，级联更新所有引用它的 `terms` 行（纯 SQLite 内部字符串级联）。

## 4. 关系类型层：单一租户表，10 种默认值只是初始种子

**结论：不再区分"全局固定"和"租户自定义"两层，统一成一张租户级表。10 种默认关系类型
只是新租户首次进入本体编辑时写入的初始种子行，业务可以删除（包括默认的）、修改名字和
例句、新增任意多行——与分类层"给默认参考、用户可增删改"的模型完全对齐。**

### 4.1 数据形态

```sql
CREATE TABLE tenant_relation_types (
    tenant_id         TEXT NOT NULL,
    relation_type     TEXT NOT NULL,   -- 需满足标识符格式校验（如
                                        -- ^[A-Z][A-Z0-9_]{0,63}$），Cypher 注入防线
    example_phrase    TEXT NOT NULL,   -- "主体 关系类型 客体"格式的例句，拼进该租户的
                                        -- 抽取 system prompt
    description       TEXT,
    allow_chain_query INTEGER NOT NULL DEFAULT 0,  -- 是否放开 2 跳链式查询，默认关闭，
                                        -- 业务自己在确认界面里手动打开
    source            TEXT NOT NULL,   -- 'default'（来自初始种子）/ 'custom'（业务新增），
                                        -- 仅用于界面展示"这是默认值"的提示，不影响任何
                                        -- 校验逻辑——default 行和 custom 行权限完全一样
    status            TEXT NOT NULL,   -- draft / confirmed（跟随本体整体的两态生命周期）
    PRIMARY KEY (tenant_id, relation_type, status)
);
```

新租户首次进入本体编辑界面时，系统自动把 10 种默认关系类型写入该租户的 `draft` 版本
（`source='default'`），业务在此基础上增删改，确认后进入 `confirmed`。

### 4.2 取消工程师人工审核

第二轮设计里"草稿→工程师审核→激活"的关卡本轮取消。原因：确认环节已经改成业务自己在
图形化界面里做最终把关（第 2 节），不再需要独立的工程审核步骤。

**保留（机械校验，自动执行，不需要人工判断）：**
- 关系类型名字必须满足标识符格式（防 Cypher 注入，这是硬性技术约束，与数据来源是否可信
  无关，任何写入路径都必须过这道检查）。
- 例句字段非空。

**取消（不再要求人工介入）：**
- 例句质量的人工评审——完全交给业务自己在确认界面里判断，代价是业务写的例句质量参差不齐
  可能拉低抽取效果，但这是"自助化"本身要接受的代价。
- 链式查询资格的人工判断——改为默认关闭，业务在确认界面里自己决定要不要为某个类型打开。

### 4.3 对现有代码路径的影响（供后续实现评估工作量）

- `llm_extractor.py::extract_candidate_relations` 需要改造成按 `tenant_id` 动态拼接
  system prompt（用该租户 `confirmed` 版本里的关系类型+例句列表），不再是一份全局常量。
- `neo4j_client.py::merge_relation` 的白名单校验从纯内存 `frozenset` 改成查询该租户
  `confirmed` 版本的关系类型表（可加缓存，因为确认动作不频繁）。
- `query_subgraph` 的 2 跳链式查询需要按租户动态拼接"该租户 `allow_chain_query=1` 的
  类型列表"，不能再硬编码 `REQUIRES|PRECEDES|PART_OF`——拼接内容必须限定为已通过标识符
  格式校验的类型名，审慎程度类比原设计文档"2 跳路径每一跳都必须精确校验 tenant_id"那条
  强调。

### 4.4 修改/删除已有真实数据在用的关系类型

见第 7 节"孤点数据保护规则"。

## 5. 属性层（本轮新增，取代前两轮"不做"的结论）

**结论：每个 `term_type` 可以声明一组额外属性字段（字段名列表），具体术语再填这些字段的
值。字段名和字段值都是自由文本，不引入类型系统（不做枚举/数字等校验），默认给参考示例，
业务可增删改。**

### 5.1 数据形态

概念上，`term_type` 枚举表（第 3 节）每一行增加一个字段列表：

```
term_type = "错误码"
extra_fields = ["严重等级", "影响范围"]   -- 默认参考示例，业务可增删改
```

具体术语（`terms` 表某一行，`term_type = "错误码"`）填写这些字段的实际值：

```
严重等级 = "高"       -- 自由文本，不限制取值
影响范围 = "全站不可用"
```

### 5.2 为什么不做类型系统

现阶段没有具体业务场景需要"严重等级只能是高/中/低"这类枚举校验，引入类型系统意味着要
再做一套字段类型编辑器（选类型、选举可选值……），本体编辑界面的复杂度会明显上升，而
现在没有真实需求支撑这个投入——沿用项目一贯的 YAGNI 判断。以后如果出现具体的、需要强
校验的属性场景，再单独评估。

### 5.3 写入侧不存在注入风险

与关系类型不同，Neo4j 属性可以用参数化的 map 写入（`SET n += $props`），属性键名本身
不需要拼进 Cypher 字符串——`sync_term()` 现有的 `SET t.type = $type, t.product_line =
$product_line` 已经是这个模式，扩展成动态属性只是把固定的两个 `SET` 子句换成一个
`SET t += $props`，不需要额外的标识符格式校验（虽然实现时仍建议做基本的字段名长度/字符
限制，避免异常输入导致的其他问题，但这不是注入防线意义上的强制要求）。

### 5.4 移除属性字段的处理

见第 7 节"孤点数据保护规则"。

## 6. Domain/Range 约束：硬约束，唯一来源是确认界面声明的表

**结论：不符合已确认 schema 的关系候选，不自动写入图谱，转人工审核队列——不是软标注，
是真正的写入拒绝。约束表的唯一来源是业务在确认界面里声明的允许组合，取消第二轮设计的
独立统计自举表。**

### 6.1 为什么这轮改成硬约束

前两轮软约束的理由是"没有真实数据支撑、怕过早约束误杀"。但本轮的整体模型变了：约束不再
是系统凭空猜的，而是业务在看到完整 schema 之后、在图形化确认界面里**主动声明并确认**的
规则——已经不是"没有数据支撑的拍脑袋"，而是业务郑重签字确认的产物。硬约束在这个前提下
是合理的。

### 6.2 数据形态

```sql
CREATE TABLE term_type_relation_allowlist (
    tenant_id           TEXT NOT NULL,
    subject_term_type   TEXT NOT NULL,
    relation_type       TEXT NOT NULL,
    object_term_type    TEXT NOT NULL,
    status              TEXT NOT NULL,  -- draft / confirmed
    PRIMARY KEY (tenant_id, subject_term_type, relation_type, object_term_type, status)
);
```

业务在确认界面里勾选/声明"这个类型组合是允许的"，可以给默认参考示例（比如根据已选的
分类和关系类型，系统自动生成一些"看起来合理"的组合供业务确认/删除），业务可自由增删改。

### 6.3 写入侧的拒绝路径

`merge_relation()` 写入前检查 `(subject.term_type, relation_type, object.term_type)` 是否
在该租户 `confirmed` 版本的允许表里：
- 在表里 → 正常写入（`AUTO_MERGED`），行为不变。
- 不在表里 → **不自动写入**，转人工审核队列，`reason="domain_range_violation"`，携带
  subject/object 的标准名、`relation_type`、`evidence` 原文——不是直接丢弃，人工还能救回来。

### 6.4 取消独立的统计自举表

第二轮设计的"从已批准数据统计组合出现次数"这张表本轮取消——硬约束下，不合法的组合根本
不会自动写入图谱，"统计已批准数据"这件事本身就失去了意义。

**用审核队列的分组统计代替**：业务在审核 `domain_range_violation` 记录时，如果发现某个
组合**反复出现**（说明这是真实存在但 schema 遗漏的合理关系），可以据此判断要不要回到
本体编辑界面里把这个组合加进允许表、重新确认——这是一个自然的、数据驱动的 schema 迭代
反馈环，不需要额外的统计基础设施。

## 7. 孤点数据保护规则

本体是会持续编辑的，编辑动作对已有数据（已经在 Neo4j 里的边和节点属性）的影响，逐项
明确如下：

| 编辑动作 | 对已有数据的影响 | 理由 |
|---|---|---|
| 删除 `term_type`/`product_line` 枚举值 | **阻止**，需先把引用它的术语改到其他类型 | 这两个字段是 `terms` 表的硬约束外键，删除在用的值会让已有术语行结构失效——这不是"孤点"而是"直接损坏数据完整性"，必须阻止，不是"允许但警告"就够 |
| 删除关系类型 | **允许**，已写入 Neo4j 的旧边保留原类型不变，仅影响以后的新写入 | 关系类型表只是写入时的白名单闸门，不是任何表的外键约束对象；旧边不因为闸门关闭而失效，`query_subgraph` 的 1 跳查询不按类型过滤，旧边依然可查——不存在"数据不可用"的风险，只需要在确认界面提示"已有 N 条现有边使用此类型"，让业务知情后自行确认 |
| 改名关系类型 | **不自动迁移**；确认界面提示已有 N 条边使用旧名字；业务可选择触发一个后台异步迁移任务，把旧边批量改成新类型（新建新类型边+复制属性+删旧边，Neo4j 关系类型不可原地修改，只能这样做） | 改名意味着"这个概念还在，只是换了名字"，与删除的语义不同——放着不管会导致同一语义在图谱里同时存在新旧两种类型字符串，长期看确实需要一条迁移路径，但不做成强制自动执行（大量边时是真实的性能/事务开销，交给业务自己决定要不要现在做） |
| 移除 `term_type` 声明的属性字段 | **保留**节点上已写入的旧属性值，仅本体编辑界面不再显示/不可编辑；日后重新加回该字段，旧值会自然重新出现 | 与关系类型删除同一思路——字段声明只是编辑界面的元数据，不主动触碰已写入的 Neo4j 节点属性，避免一次误删字段定义就永久丢失已有数据 |
| 修改 domain/range 允许表（删除某个组合） | 不影响已经写入的旧边（旧边已经存在，不会被回溯删除）；仅影响以后新抽取的候选是否会被拒绝转审核 | 硬约束只在写入那一刻生效，不是持续校验已存在的边 |

**一条贯穿全表的原则**：本体编辑（分类、关系类型、属性字段、约束表）改动的都是"schema
配置"，不会主动触碰已经写入 Neo4j/SQLite 的实际数据行。唯一的例外是"关系类型改名"提供
的可选迁移任务——这是业务主动触发的、明确知情的操作，不是编辑 schema 本身的副作用。

## 8. 范围之外（不做）

- **基数约束**（某关系每个节点最多几条边）——三轮讨论下来都没有出现具体业务场景需要，
  维持明确不做。
- **属性字段的类型系统**（枚举/数字等校验）——第 5.2 节已论证，没有真实需求支撑这个
  投入，字段值统一按自由文本处理。
- **关系类型编辑的工程师人工审核**——第 4.2 节已论证，图形化确认界面本身就是安全网，
  取消了这道关卡，机械格式校验（防注入）仍然保留且不可关闭。
- **domain/range 允许表的统计自举来源**——第 6.4 节已论证，硬约束模型下这张表失去意义，
  改用审核队列的分组统计做反馈信号。
- **关系类型改名的强制自动迁移**——第 7 节已论证，迁移任务由业务按需触发，不做成编辑
  本体时自动执行的强制步骤。
