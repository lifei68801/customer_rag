# 前台与管理后台共用一套会话 —— 设计

**目标：** 把前台问答从「匿名、租户硬编码」改成「登录后使用、身份与租户来自服务端会话」，并让前台与管理后台共用同一套 Cookie 会话——登录一次，两边都不再需要登录界面。

**产生方式：** 2026-09-04 的逐问盘问。用户最初问的是「登录挪到前台之后后台还要不要登录界面」「后台左下角的账号块能不能挪到前台」，盘问过程中确认前台面向的是**内部坐席**而非终端客户，问题因此从 UI 摆放升级成认证边界的重构。

---

## 背景：为什么这不是 UI 摆放问题

前台（`/`，`ChatPage`）今天**完全没有身份认证**：

- 租户是硬编码常量：`frontend/src/hooks/useAgentChat.ts:12` 的 `const TENANT_ID = 'demo'`
- 用户身份是 localStorage 里的随机 UUID：`frontend/src/lib/identity.ts::getAnonymousUserId`，其注释明说「这个产品目前没有真实的客户登录系统」，并记下了已知代价——换浏览器/清缓存/隐私模式就换个身份、看不到旧会话
- 五个接口无任何鉴权依赖：`POST /agent/chat`、`POST /qa`、`GET /agent/sessions`、`GET /agent/sessions/{id}/messages`、`DELETE /agent/sessions/{id}`。三个 router 都是裸 `APIRouter()`，没有全局 `dependencies`

后台是另一套：token 存 `sessionStorage`（`useAdminAuth.ts:4`），服务端每个 `/api/admin/*` 路由挂着 `require_admin_session` / `require_admin_role`，`deps.py:384` 那道 `member` 越权 403 是「整个账号体系唯一真正的安全边界」（该函数 docstring 原话）。

**所以前台和后台不是同一个应用的两个界面，是一个匿名公开应用和一个认证应用。** 后端启动时那条警告说的正是前者：

> gateway_shared_secret 未配置：当前应用信任客户端自报的 tenant_id，任何调用方都可以伪造租户身份绕过多租户隔离。

还有一个今天就存在、与本设计同源的问题：`session_routes` 的 `user_id` 是 URL 明文参数，**任何人换一个 `user_id` 就能读别人的会话历史**，那几个接口没有归属校验。

## 已确认的四条决定

| # | 决定 | 否决了什么 |
|---|---|---|
| 1 | **坐席复用现有 `admin`/`member` 账号体系**，`member` 即坐席；专门的「坐席」角色延后设计 | 不新增角色（它与 `member` 的唯一差别「能否进后台」今天已由页面级权限表达，再加角色是在同一件事上引入第二套判据）；不做两套独立账号（同一个人两份密码，停用要停两次，「停用立即生效」会出现漏洞） |
| 2 | **既有匿名会话历史直接废弃，不迁移** | 不做「首次登录认领」（要在登录这条关键路径上加一段只在过渡期有用的逻辑，出错代价是把 A 的会话过户给 B）；不做批量迁移（按一个随机 UUID 无从判断该归谁） |
| 3 | **会话载体改用 HttpOnly Cookie** | 不用 `localStorage`（token 长期留在磁盘、XSS 可读）；不维持 `sessionStorage`（按标签页隔离，新开标签页仍要重登，达不到目标） |
| 4 | **「当前租户」进服务端会话**，前后台共用 | 不在前台另放一个租户选择器（会造出两个可以互相矛盾的「当前租户」，即界面显示与实际生效脱钩） |

## 设计

### 1. 认证边界（服务端）

给五个接口装门，并把两处身份来源从「客户端自报」改成「从会话取」：

| 接口 | 改动 |
|---|---|
| `POST /agent/chat` | 要求会话；租户从会话取，**忽略 body 里的 `tenant_id`** |
| `POST /qa` | 要求会话 |
| `GET /agent/sessions` | 要求会话；`user_id` 从会话取，**移除该查询参数** |
| `GET /agent/sessions/{id}/messages` | 同上 |
| `DELETE /agent/sessions/{id}` | 同上 |

前台自此走与后台同一道 `deps.py:384` 的租户校验：`member` 的租户由会话决定，服务端不再接受客户端自报；`admin`（`tenant_id` 为 `None`）可访问任意租户。

**`X-Tenant-Id` 网关头那条回落路径对这五个接口就此失效**（落地后核实的实际结果，与本节初稿的设想不同）。`get_gateway_tenant_id` 函数本体没改，但它挪到 router 级依赖之后返回值不再有人接，这三个 router 下也没有任何地方再调 `resolve_tenant_id`：网关头只携带租户、不携带用户身份，而这五个接口现在都需要 `user_id`，回落时无处可取。失效方向是 fail-closed——没有会话就是 401，不存在「不带会话、只带 `X-Tenant-Id` 就进得去」这种绕过。

**代价是一个很难排查的故障形态**：这三个 router 上仍挂着 `get_gateway_tenant_id`，一旦某个部署配置了 `gateway_shared_secret`，它就会要求**每一个请求**都带对 `X-Gateway-Secret`，而浏览器自己发不出这个头；`/api/admin/*` 没有这个依赖。于是流量若没有真的经过那台会注入该头的网关，表现是「后台一切正常、前台五个接口全线 401」——这个形态几乎不会让人想到网关密钥配置。

### 2. 会话与租户的载体

**不改会话存储本身。** `AdminSessionStore`（`app/api/admin_session.py`）是进程内字典、8 小时 TTL、不持久化。它的 docstring 给出了不用 JWT 的理由——「JWT 签发后撤销不了，『禁用账号立即生效』就做不到」——这个判断继续成立。Cookie 里装的仍是那个不透明 token，服务端仍按字典查、仍能即时吊销。**变的只是传输与存放方式。**

**登录**：`POST /api/admin/login` 除继续返回 body（兼容既有调用方）外，额外下发：

```
Set-Cookie: <name>=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=28800
```

`Secure` 标志**按请求是否经 HTTPS 动态决定**，不写死——本地 `http://localhost` 开发时带上 `Secure` 会让 Cookie 直接不生效。

`SameSite=Lax` 让跨站发起的写请求带不上 Cookie，挡掉绝大部分 CSRF；同站导航（前台点进后台）照常携带。

**CSRF 双提交令牌**：登录时同时下发一个**非 HttpOnly** 的随机值，前端每个写请求（POST/PUT/DELETE）放进 `X-CSRF-Token` 头，服务端比对两者。为什么在 `SameSite=Lax` 之外还要这一道：`Lax` 对老浏览器不完全可靠，而这一道的成本只有前端一个请求拦截器加服务端一个依赖。

**登出**：清 Cookie **且**从字典删 token。只清 Cookie 的话 token 还活在服务端，8 小时内谁拿到它仍然有效。

**当前租户进会话**：`AdminSession` 增加可变字段 `current_tenant_id`；切租户成为 `PUT /api/admin/session/tenant` 的服务端调用，前端不再自己在 `sessionStorage` 里记。校验规则不变：`admin` 可切任意（仍走 `require_active_tenant_or_404` 确认租户启用着），`member` 只能是自己那个，切别的 403。

**会话失效的界面契约**：会话是进程内的，**后端一重启所有人都要重新登录**。这今天已是事实，但 Cookie 会让它更刺眼——浏览器里 Cookie 还在、看起来像登录着，服务端却已不认。因此前端拿到 401 必须主动清本地状态并跳登录页，**不许停在「显示已登录但什么都点不动」的界面**，也不许反复重试。

### 3. 前台的登录门与账号信息块

**`/admin/login` 路由保留。** Cookie 同源共享之后它不再是常规入口，但它是会话过期或被吊销时的落点；删掉的话那两种情况下用户会撞进白屏。

**前台加一道登录门**：`/` 未登录时渲染登录表单，**复用现有 `LoginPage` 的组件，不新写一套**；登录成功后进问答界面。

**账号块不是「挪到前台」，是共用组件、两处渲染，内容按场景裁剪**：

| 条目 | 前台（问答） | 后台 |
|---|---|---|
| 当前租户 + 用户名 | ✅ | ✅ |
| 切换租户（仅 `admin` 可见） | ✅ | ✅ |
| 设置 / 改密码 | ✅ | ✅ |
| 登出 | ✅ | ✅ |
| 账号管理 / 租户管理 | ❌ | ✅ |

后两项不进前台的理由不是权限（服务端已挡住 `member`），而是**前台是「用知识库」的地方，后台是「管知识库」的地方**。把管理入口塞进问答界面，等于把「建模 → 接入 → 审核」这条流程的入口散回一个不属于它的页面。

前台**给 `admin` 显示租户切换器**：换租户即换知识库，而 `admin` 需要验证「我刚配好的本体，问答到底通不通」——那正是他最需要前台的时候。

前台右上角的「管理后台」入口保留，此后是同一套会话内的跳转，不再需要二次登录。

## 实施顺序：分两步

**第一步只做服务端（本设计第 1、2 节）。** 它独立可交付，做完之后「任何调用方都可以伪造租户身份」这条启动警告只对 `/voice/*` 还成立（那两个接口仍是匿名入口、租户仍取客户端自报的 query 参数，不在本设计范围内），警告文案已按这个范围改窄。

**第二步做前端（第 3 节）。**

两步之间系统并非完好——服务端加门之后前台会 401，所以第二步必须紧跟。分开的意义在于**评审与回滚的粒度**：服务端的认证边界和前端的界面重排是两类风险，混在一个提交里，回滚其中一半会连带另一半。

## 影响面（实测）

| | 数量 | 说明 |
|---|---|---|
| 前端用 `adminFetch` 的文件 | 21 | **不用改**——改的是 `adminFetch` 内部：去掉 `Authorization` 头，加 `credentials: 'include'` 与 CSRF 头 |
| 前端读写 `sessionStorage` 的文件 | 35 | 生产代码只有 `useAdminAuth.ts` 与 `TenantContext.tsx` 两处；其余是 28 个测试文件各自的 `signIn()` 助手 |
| 后端带 `Authorization` 的测试处 | 138 | 绝大多数不受影响——它们用 `dependency_overrides` 覆盖了 `require_admin_session`，那个头是摆设 |
| 后端调 `/agent/*` 或 `/qa` 的测试文件 | 11 | 其中直连这些接口、未覆盖依赖的那些要重写请求形状 |

**会真正被打断的三类**：

1. `session_routes` 的签名变了（去掉 `user_id` / `tenant_id` 查询参数），直连这些接口的测试要重写。
2. 前端 28 个测试文件的 `signIn()` 助手——往 `sessionStorage` 塞 token 的模拟方式失效，要改成 stub `whoami` 或注入 Cookie。琐碎但不能省。
3. `frontend/src/lib/identity.ts` 整个删除（`getAnonymousUserId`）——身份不再来自 localStorage。

## 测试

按本项目既有实践：每条负向断言都要故意改坏实现确认它变红；变异不变红时先确认变异真的落进了文件。

**越权是重点，这两条今天完全没有测试**（因为今天根本没有这道门）：

- `member` 带自己的会话去问**另一个租户**的资料 → 拿不到（原文写的是「→ 403」，落地后这个结果已不可能出现：租户不再由客户端提供，请求里的 `tenant_id` 被静默忽略，所以没有可拒绝的越权请求。等价保证由 `tests/api/test_qa_routes.py:132` 的「`member-t2` 问 t1 的资料，`used_sources` 为空」与同文件 `:169` 的「会话租户压过 body 和网关头」两条给出，两条都能真正区分对错实现）
- 换一个 `session_id` 去读**别人**的会话历史 → 拿不到

**其余必测**：

- 五个接口逐个：未登录 → 401
- 缺 `X-CSRF-Token` 的写请求 → 拒绝
- Cookie 在但服务端已重启/吊销 → 401 → 前端清状态跳登录页（断言不能停在「显示已登录但点不动」）
- `admin` 切租户成功、`member` 切别的租户 403
- 登出后同一个 token 再用 → 401（证明服务端也删了，不只是清了 Cookie）

## 明确不做

- 不新增「坐席」角色（决定 1，延后设计）
- 不迁移既有匿名会话历史（决定 2）
- 不改 `AdminSessionStore` 的进程内字典实现，不引入 JWT
- 不动 `X-Tenant-Id` 网关认证路径的**代码**（函数本体确实一字未改；但它对这五个接口的**效果**已经作废，见第 1 节）
- 不把账号管理 / 租户管理入口放进前台

---

## 待定

**会话持久化。** 进程内字典意味着后端重启即全员登出。今天如此，本设计不改变它。是否要把会话落到 SQLite/Redis 是一个独立决定——它的收益（重启不掉线）与代价（多一处状态、吊销逻辑要跨进程一致）都不小，且与本设计正交。等本设计落地、真实使用中重启掉线成为实际困扰时再单独决定。
